# Maintenance

## Validation

Run `npm run build`, `npm test` and `cargo check --manifest-path src-tauri/Cargo.toml --locked` for frontend and Rust checks. `npm run test:tauri` builds and runs the isolated native integration suite; `npm run test:tauri:run` reuses its existing test build. The suite uses temporary app data and a local mock model, not real devices or provider credentials. CI runs native integration tests on macOS and Windows; see the [CI workflow](../.github/workflows/ci.yml) for the full matrix.

On macOS, native integration tests run in the background by default: the main and simulator windows stay hidden, the test app cannot activate, and no test tray icon is created. WebDriver still drives the real WKWebViews, IPC and storage. To display the windows for debugging, run `npm run test:tauri -- --foreground` (or `npm run test:tauri:run -- --foreground` to reuse the build). Direct `node --test` runs use the same background default; set `GIZMOTH_E2E_FOREGROUND=1` to display them. Tests that explicitly verify native window focus need foreground mode. Windows keeps its existing visible test windows.

## Assistant runtime

The assistant uses the maintained `@earendil-works/pi-agent-core`, `pi-ai` and `pi-schema` packages at matching pinned versions. Node.js 22.19 or later is required; CI uses Node.js 24. `agent-stream.ts` explicitly dispatches the four configured API types through the SDK's lazy stream factories, retaining custom provider IDs and native credential resolution. Tool parameters use pi-schema builders; MCP-advertised JSON Schemas are adapted directly.

Pi 1.x keeps system instructions in the transcript. `agent-transcript.ts` uses a named `gizmoth` section so brief and permission updates replace their previous values without dropping conversation or tool declarations. Request preparation includes updates made during a running turn. Rewind and retry reapply the current brief and permissions after truncating historical messages. Empty-chat controls count conversation records rather than SDK system records. Stored chat keeps only conversation and tool-result messages; current instructions and tool declarations are rebuilt from the project brief and permissions on load.

## Assistant simulator tools

The assistant exposes `list_simulators`, `run_in_simulator`, `inspect_simulator`, and `press_simulator_button`. Simulator runs use the project's run permission: `ask` requires explicit confirmation for each install/run and binds subsequent button approval to that specific request, `allow` runs directly, and `deny` prevents firmware startup, installation, and input. Choosing a simulator in the Run dialog also routes the legacy `push_to_device` tool to that simulator; choosing a physical device clears this routing. Local simulator testing never falls back to the remote device service. Run tools ignore deleted remembered IDs when choosing a remaining simulator or creating one; explicitly requested unknown IDs fail. Local routing intent remains in place through declined or failed recovery and changes to the replacement ID only after its window opens successfully, so a legacy-tool retry cannot fall through to physical hardware.

The control channel uses the existing window token, validates commands in the receiving window, and ties each request to the project's current app snapshot. Only startup, inspection, and bounded physical-button presses are exposed; arbitrary firmware commands and shell execution are not. Run authorization is rechecked after project preparation and profile creation, immediately before opening or retargeting. Denying run access invalidates queued assistant-owned app requests and notifies their windows to abort pending startup and Lua admission; tightening `allow` to `ask` cancels unconfirmed queued requests. Explicitly confirmed requests retain their consent under `ask`, and explicit user Run requests are preserved. Preparation rechecks `ask` as well as `deny` before dispatch. Each assistant invocation allocates its own app request ID before opening the window. Its abort signal invalidates only that exact assistant-owned request, including during native opening or queued startup, and preserves a newer UI Run. The signal remains connected while the assistant produces its follow-up because queued startup can outlive the tool's status reply. Readiness retries and startup retain the original ID and reject supersession; button consent is recorded only after that same request's startup control returns. An SDK installation already accepted before cancellation may finish safely, but its canceled waiter cannot power on or launch Lua. Simulator operations reserve a per-project selection generation before their first asynchronous preparation step and retain it through validation, project lookup, profile creation and window opening. Admission checks that original generation before changing the active session, so late assistant preparation cannot replace a newer UI Run. Route commits use it too, so late opening cannot overwrite a newer hardware choice. Agent input uses a separate source tracker and SDK presses with `releaseOnBlur: false`, so editor focus changes release keyboard/pointer input without shortening a programmatic hold. Retargeting, cancellation, shutdown, pagehide, and destruction still release these holds. Captures copy the live framebuffer with its actual brightness into a 240×240 PNG. All models can request capture dimensions, brightness and hash. PNG content is forwarded only when the current model supports images; text-only models receive the metadata without pixel data.

Cancellation notifications carry the exact app request ID. The receiving window aborts that app waiter synchronously before requesting another snapshot, and retains early cancellations until the preview registers its cancellation handler. Canceled IDs also block stale snapshot admission. A delayed cancellation affects only matching app/control requests, preserving a newer UI run and its inspection/input controls.

A failed simulator run tool invalidates its own queued execution request before returning the original failure, so delayed SDK work cannot silently resume that request. Native open completions verify session/request ownership and the current target generation before broadcasting retargets. An outdated target invalidates that execution and reports supersession instead of success. Execution-only cancellation preserves already-running inspection controls as well as future read-only calls; already-invalidated executions do not rebroadcast when another permission changes.

For a new browser simulator without transient user activation, the assistant finishes preparation and then requests an explicit Open click immediately before opening the popup. Native windows and already-open browser simulators keep their existing flow. `npm run test:browser` exercises this in standalone headless Chrome with popup blocking enabled; embedded preview containers may reject all popups independently of user activation. The browser regression has a dedicated CI job.

Selection keeps pending/incomplete local intent separate from the last committed simulator ID. `list_simulators` reports `selectionPending`. While it is true, legacy dispatch and implicit inspection/input reject instead of using physical hardware or the previous simulator; an explicit simulator ID remains available for scoped inspection. Successful local commit clears the marker, and an explicit hardware choice clears local intent. Failed or declined local preparation retains the guard until a target is chosen again. Hardware rows in the workspace Run dialog provide **Select only**: it clears unresolved local selection and selects that hardware without installing or running the project. Assistant-led hardware execution remains a separate action under the current run permission, including its own confirmation under `ask`.

Hardware dispatch captures the current project target-selection generation before validation and rechecks it before install and run, so a newer simulator choice supersedes the older physical-device invocation. Overlapping opens of one native simulator share the same in-flight native-opening Promise; the successor retargets only after that reservation finishes. A test-only manual opening gate verifies this against the backend's actual `OPENING` reservation.

Each project session counts run-permission denials. Simulator and hardware preparations capture that counter and reject an intervening revocation even if permission has since returned to `ask` or `allow`; an old confirmation cannot revive the invocation. Cancellation clears the execution binding but preserves a separate inspection ID and cached project snapshot. The simulator applies the canceled snapshot in its layout commit, checks the marker directly before request side effects and in status reads, skips automatic startup and keeps status/capture available to the original project. Read-only bindings cannot authorize startup or input and are replaced by retargeting or removed on close.

Run-permission changes cancel active assistant startup and input controls independently of app ownership, including controls queued for channel readiness. A UI-owned app request remains valid while its assistant-held button is released. Read-only inspection remains available. Profile lookup and confirmation entry both check cancellation, so a stopped preparation cannot open a stale consent dialog.

Player `phase: running` describes firmware lifecycle. App `status: run-requested` records launch acknowledgement only. Inspection reports host installation/input events and command errors, not Lua runtime logs or a pass/fail verdict. Dismissing the temporary-app notice hides only its presentation: a later failure still records the current request's error for assistant inspection. When a stopped wait settles, both normal early returns and caught errors record terminal `canceled` status for the still-current request. That status remains observable after dismissal; superseded request outcomes are ignored. First-boot setup may keep app launch waiting; inspect the screen and complete it with device buttons. Do not treat successful packaging or launch admission as proof of correct app behavior.

## Live simulator validation

After `npm run test:tauri` builds the isolated native fixture, run the live simulator check:

```bash
GIZMOTH_LIVE_SIMULATOR_TEST=1 node --test --test-concurrency=1 test/integration/simulator.test.mjs
```

These opt-in checks download the provider's current H106 Tiga Trial firmware. The agent startup regression creates a simulator through a synthetic model tool call, boots it without host Power clicks, captures its framebuffer, and advances the actual first-boot key lesson through an agent button command. It then holds the tail of a real Reload shutdown after the player reports `stopped`, verifies that a concurrent agent startup cannot destroy or replace that player, and releases the barrier before checking Reload finishes. The persistent-device regression starts from Run on a fresh simulator without opening the firmware picker or pressing Power, then exercises command-interface startup, BUSY handling, cancellation and run-only retry, completes setup with the device keys and checks the Lua framebuffer. It also sends framebuffer images through the model's vision transport, exits Lua through an agent Back hold, and reruns the selected simulator through the legacy `push_to_device` tool. It also exits through the physical Back long-press and runs the project again through the chooser in the same device window. It closes the simulator normally, restarts the application process and verifies the same origin, completed setup and installed app without reinstalling. A second device with the same model must have separate preferences and apps; deletion must clear only its own data. The separate `simulator-storage.test.mjs` check verifies real localStorage and IndexedDB persistence across process restart, UUID isolation, owner-scoped destruction and deletion from both the manager and device window without starting network/media firmware. It uses the same opt-in variable and runs in macOS/Windows CI after the native agent suite. On systems affected by the WebKit encoded-audio worker crash, the full firmware check can also set `GIZMOTH_DISABLE_RTC_TRANSFORM_TEST=1` to test with that browser capability unavailable; radios, real commands, Lua execution and persistent data remain active. The opt-out is applied by a native-e2e-only document-start script to every simulator frame, including automatically started and replacement firmware, before app_host scripts execute. This is a test boundary, not a production WebKit fix. It uses temporary application metadata and isolated UUID data stores, without pairing hardware or reading provider credentials. Screenshots and failure diagnostics are written to `src-tauri/target/native-e2e-results/`. On Windows the harness observes each actual asynchronous result through a fresh per-script page slot and synchronous inspection: WDIO 1.5.1 otherwise reuses a native async handler by window label after that WebView has been destroyed. Storage and firmware operations themselves remain real. A Windows-only native regression injects initial tracking failure before PID lookup, handle capture and event subscription, then verifies update preparation and deletion recover through the retained environment without reopening the simulator or restarting the app. A separate Windows regression makes close-time PID getters fail and exercises normal close, manager/device deletion and updater preparation against real native windows and processes.

The local-flow diagnostic can be reproduced with `GIZMOTH_OFFLINE_AFTER_INSTALL_TEST=1 GIZMOTH_LIVE_SIMULATOR_TEST=1 GIZMOTH_DISABLE_RTC_TRANSFORM_TEST=1 node --test --test-concurrency=1 --test-name-pattern='native simulators retain' test/integration/simulator.test.mjs`. It enables both simulated radios for package installation and switches to the SDK's offline preset only after acknowledged installs. Restored sessions wait for local command registration before applying the diagnostic preset. All Lua commands, framebuffer checks, input, restart, storage, device-isolation and deletion assertions remain real; a pass here does not establish online Trial/WebRTC interoperability. The test records Lua entry and first-present markers, timestamps command admission and interface changes, and reports a terminal host error immediately. After leaving Lua it uses real Back presses to leave the app list and Apps entry before asserting idle Home for the next API request.

Each simulator's model is immutable. On macOS 14 and later, its UUID identifies a persistent `WKWebsiteDataStore`; Windows/Linux use `simulators/<uuid>/webview` under app data. The loopback port in `simulator-runtime.json` is retained across launches because IndexedDB and localStorage are also origin-scoped. An occupied saved port fails explicitly rather than silently creating an empty storage origin. The loopback server uses async HTTP/1 with keep-alive disabled, known content lengths, at most 32 active connections, a five-second header deadline and a fifteen-second connection deadline. It serves only the bundled entry, flat assets/WOFF2 fonts and owner-bound packages; strict Host, method and isolation policies remain in force. macOS before 14 cannot provide independent UUID stores and receives an explicit simulator error; other application features keep their existing minimum OS version. Normal Close and orderly application Quit await the firmware shutdown barrier. Only confirmed deletion destroys the simulator and removes its native data store. The simulator's close command accepts no target label and can destroy only its caller. Native Close and self-deletion share one frontend teardown state: deletion owns destruction once confirmed, and closing disables later delete confirmation. The backend also checks window liveness while registering deferred self-deletion under the Destroyed-handler lock, so a late IPC cannot strand a deletion reservation. Both manager and device-window deletion register their pending cleanup under the same lock as `Destroyed`, rechecking that the window still exists. If normal Close has already finished, manager deletion proceeds directly to storage cleanup; if `Destroyed` has already taken responsibility when destruction reports an error, the manager keeps awaiting that cleanup. This prevents a missed event from stranding the deletion reservation. Windows retains the controller's native COM environment on the UI thread before initial tracking can fail, then waits for the matching WebView2 `BrowserProcessExited` event before removing the data directory. If close-time controller PID lookup fails, it preserves an existing confirmed exit or pending retained-environment watch; otherwise it can capture environment processes without a controller PID. A failed `Close()` on that PID-unavailable recovery path permits native window destruction while storage cleanup still waits for genuine process-exit confirmation. A failed initial setup leaves a pending record; deletion and Quit/update retries can capture fresh process handles from that retained environment even after the failed window has been destroyed. Failed-open destruction immediately starts independent confirmation, including when Quit/update is already waiting on that opening. If the UI callback never retained an environment, failed opening preserves the live window for a later close retry. Missing/unreadable event arguments or a mismatched PID leave tracking pending and retain the environment and handles for a later notification or independent confirmation. If the notification is missing or inconclusive, an independent check requires every captured process handle to signal exit and a fresh UI-thread environment query to report no associated processes. Handles pin process objects against PID reuse; both checks and completion belong to the same window generation. Normal Close and update preparation use the same confirmation. Successful confirmation releases the captured process handles. A new Quit/update attempt restarts confirmation for already-closed views whose earlier monitor timed out. This confirms release of the browser's associated runtime processes and user-data resources, so recreating a deleted UUID cannot reuse a half-closed database. Failed registration, an uncertain process query or a 30-second process-exit timeout retains the profile for retry. Residual Windows file-sharing and directory-content contention is retried for up to ten seconds. Orderly Quit also waits for tracked browser processes before exiting.

A Run request explicitly boots firmware before sending Lua commands. SDK `enter()` installs firmware and stops at `ready`; the host must call `start()` and await `running`. An already-running device is reused, and a stopped/spent runtime is reinstalled before starting. Runtime startup, including firmware installation, has a 60-second deadline. Canceling an installation waiter immediately releases the request without aborting the underlying SDK operation; another request on that player joins the same installation rather than starting another one. Cancellation is checked before power-on. Canceling after installation leaves the ready runtime available to Retry without Power. Readiness is tied to the current SDK controller identity, so Reload cannot consume a pending Run using the previous controller's loaded state. A failed or canceled startup unlocks Retry and Reload even if the SDK still reports `starting`; explicit recovery recreates that unfinished runtime, while one that has since become ready/running is reused. Opening the same simulator from its manager clears any incoming Run request; if this cancels unfinished startup without a successor request, Reload remains available to recover it. Simply opening a model remains a preview until it receives Run or physical input.

A new Trial session may require first-boot setup before it accepts Lua app launches. Keep the screen and all device keys available while waiting. The released firmware can temporarily detach its local command interface while network owners stop or rebuild, and while a Lua app owns the device resources. Hold Back to exit the current app before sending another project. Command discovery waits up to 60 seconds for the interface; rejected launches wait up to 120 seconds. Automatically retry only explicit BUSY/resource-exhausted rejection or the SDK's missing-interface check before submission. A timeout does not establish whether a launch was accepted. A definitive PAL `-8` or wrapped RPC `5` from launch invalidates only that request's acknowledged-install cache, so the next explicit Retry reinstalls the missing app; it does not automatically replay installation.

The released Trial firmware can turn off its backlight while network teardown delays a launch. A green firmware framebuffer with brightness zero is a sleeping display. Short-press the device Power key to wake it; preserve its brightness and sleep preferences rather than overriding them from the host. The native check uses the actual Power key when needed and samples the visible preview framebuffer.

### Player lifecycle patch

`npm ci` applies `patches/@gizclaw+models-player+0.7.0.patch` through `patch-package`. It moves the SDK's readiness check from animation frames to a 25 ms startup timer, stops polling once running and cancels pending polling during shutdown or destruction. This allows command admission while the editor has focus. The host also keeps a low-rate framebuffer copy when WebKit pauses background paint callbacks, and refreshes immediately on visibility changes. Window creation releases the profile/settings locks before native UI calls so concurrent profile reads cannot deadlock the UI thread.

With the Vite preview running, open `/test/browser/player-lifecycle.html` for a deterministic real-DOM regression. It mounts the actual SDK through its runtime driver seam, withholds all paint callbacks and verifies readiness, command admission, shutdown and destruction. Its synthetic runtime tests lifecycle behavior; real firmware execution belongs to the native check. The patch also adds explicit focus-independent button sources and separates `releaseUserInput()` from lifecycle `releaseAll()` across the SDK's buttons, scene, and play controllers. Unit checks cover blur, cancellation, pagehide, and destruction; the native firmware regression measures the actual pressed edge duration while focusout, blur, and hidden-document handlers fire. Remove the patch only after the replacement SDK passes these checks.

## Update shutdown barrier

Before installation or a restart-only retry, the updater saves project state and awaits the native simulator shutdown barrier. This runs before installation because the Windows installer can exit the app itself; relaunch requests can also bypass Tauri's exit prevention. The main-window-only preparation command blocks new simulator opens and deletions under the registry lock, waits for opening reservations to finish before issuing any close requests, and waits for firmware writes and storage cleanup. Preparation and ordinary Quit share one shutdown-state observation: while holding the registry and opening locks, check reservations first, then read the current framework windows and storage state. Native close calls run only after those locks are released. Opening and deletion share the same shutdown-admission check under the registry lock. Ordinary Quit blocks both reservation types before the final readiness check and restores admission if shutdown is canceled. A window registered by the last finishing opener therefore cannot disappear from a stale success snapshot, and a newly registered window cannot be closed before its initial Windows exit tracking exists. Windows also starts independent exit confirmation from `Destroyed`, covering closes that precede frontend listener registration. The Windows fault-injection regression delays tracking before environment retention and starts update preparation during that gap. An unsuccessful attempt cancels that open guard. If ordinary Quit cannot finish shutdown within its bounded wait, the app explicitly reports cancellation in the main window and allows retry rather than silently abandoning the prevented quit.

## Serial service

`src-tauri/src/serial/` implements the resident service, launched as `gizmoth --serial-daemon --data-dir <app data>`. The desktop starts it when Service or a saved port is enabled. A stable `serial/daemon.lock` inode remains exclusively OS-locked until every worker has exited; failed HTTP readiness is never permission to steal ownership. `ports.json`, private `daemon.json` and package snapshots live under `<app data>/serial/`. The daemon exits after ten idle minutes only when both Service and all ports are disabled, or after an explicit stop.

The daemon alone enumerates OS ports, every 1.5 seconds. Desktop and MCP discovery use its cached `GET /v1/system-ports` result. Following a changed USB endpoint requires unambiguous identities among both configured and enumerated ports, plus a unique path reservation. A path change retires the old worker before opening its replacement. Retired workers cannot publish over the new connection state. An unreadable `ports.json` is moved aside as `ports.unreadable-<ms>.json` rather than overwritten.

Snapshots carry a per-process `instanceId` and an instance-local `version`. `/v1/watch?since=<version>&instance=<id>&timeoutMs=<budget>` returns immediately for a different instance; waits are capped at 20 seconds, and zero requests an immediate snapshot. Ports expose `logSeq` and `logGeneration`; log pages include `instanceId` and `generation`. Clearing increments the log generation without reusing sequence numbers. Readers invalidate old responses on instance/generation changes and serialize page reads without discarding progress on ordinary sequence updates. Logs retain 5000 entries, split long text in linear time without breaking valid UTF-8, flush partial lines after 250 ms, and flush remaining bytes once at session end. Exports capture a fixed sequence/generation range and enforce total bounds.

Plain serial requests DTR preservation instead of explicitly clearing it. Driver/open behavior remains platform-dependent; this does not guarantee that opening an adapter cannot reset a board. Raw writes use bounded partial writes and cancellation checks, without an unbounded per-frame driver drain.

### H2Loader core

`native/serial-core/` is a downstream Bazel module pinned to GizOS in `MODULE.bazel`. Its ABI 2 adapter reuses Host Core's reliable 460800 baud connection, status, package inspection, Stage transfer/verification and reboot/reconnect operations. macOS uses an adapter-owned PAL fd with advisory `flock` and a fail-closed `TIOCEXCL` request before configuration; Windows retains the upstream exclusive-open PAL. After acquiring both locks, a bounded `proc_listpidspath` check rejects system-visible holders of the actual path and its cu/tty counterpart before termios is read or configured. Query failures and possibly truncated results fail closed. Privileged bypasses, hidden descriptors and drivers that ignore `TIOCEXCL` remain outside this guarantee; close other terminals and flashers before connecting. Kernel and USB-driver enforcement require platform testing. On the tested Darwin kernel, synthetic PTYs accept `TIOCEXCL` without rejecting ordinary reopen; tests verify syscall ordering, failure handling and cleanup, not physical USB-driver enforcement. One cancellable four-second status guard covers connection, refresh, Stage status checks and reboot verification, while transfer/flash command deadlines retain 120 seconds.

Build and stage the archive before Cargo. For the host:

```bash
npm run serial-core:build
```

An explicit target can be passed instead:

```bash
npm run serial-core:build -- x86_64-apple-darwin
```

A checkout at the pinned GizOS revision can override fetching:

```bash
GIZOS_SOURCE=/path/to/gizos npm run serial-core:build
```

The Bazel targets `//:serial_pal_test` and `//:status_guard_test` exercise synthetic PTYs and a fake PAL/clock/KCP peer against the real pinned Host Core. On macOS, `//:startup_test` also checks that serial initialization creates no background threads and that the stateless memory/time services remain usable. The serial adapter skips the CLI platform startup on macOS: its filesystem mounts and system-event/default-route monitor are not needed for serial I/O. The pinned route monitor treats its own `RTM_GET` replies as network changes and can otherwise consume a CPU core even with idle devices. These tests do not enumerate or open physical devices. `.bazelrc` disables `bazel-*` convenience symlinks so Vite and editors do not crawl the execroot; the build script locates the archive with `bazel cquery`.

`src-tauri/build.rs` links `native/serial-core/dist/<target>/` when available. Without it, the UI reports that H2Loader is unavailable. PR builds and releases require `GIZMOTH_REQUIRE_SERIAL_CORE=1` on every target, so a missing macOS or Windows archive fails the build rather than producing an incomplete installer. Windows device operation remains unverified. Auto detect tries a four-second H2Loader handshake, then falls back to plain serial. Select Plain serial for devices that must not receive negotiation bytes.

### Service and port occupancy

Settings › Service configures the HTTP/WebSocket/gRPC service (`gateway.rs`, `<app data>/gateway.json`, mode 0600): default port 7420, local or LAN scope and `Authorization: Bearer <gmk_ API key>`. All interfaces use HTTP, WS and native HTTP/2 prior knowledge (h2c) without TLS or certificates. LAN scope includes Tailscale interfaces; Tailscale supplies network encryption when used. `gateway::Listeners::prepare` binds before committing a listener transaction, reuses sockets for scope switches, and retains the working configuration on failure. Remote WebSockets require the bearer header and reject token query parameters. Local and remote connections have independent budgets. The 1.5-second service poller reconciles interface changes without changing authorization; enumeration failures keep working listeners, while an empty list retains loopback. Recoverable binds are retried and new URLs are published only after listener adoption. The app's private token works only through the dedicated loopback listener: even a request originating on this computer through a LAN listener cannot acquire app identity, and proxy headers are ignored. Only app callers can change Service settings, approval policy or shut down the daemon. Disabling Service, rotating its key or narrowing its scope revokes affected Gateway sessions and waiters; a port-only rebind preserves authorization.

If the configured port is occupied on loopback or an enabled LAN interface, startup and manual listener changes try successive ports, wrapping from 65535 to 1024. The selected port is saved in `gateway.json` and shown in Settings. Other recoverable startup bind failures retain private loopback control and retry the configured target. Manual listener changes save desired settings first, but bound addresses, URLs and `daemon.json` continue to identify the active listener until adoption succeeds. Failed candidates are retained and retried in every scope, including Local and disabled Service.

`WS /v1/ports/{id}/pipe?client=&title=` implements `gizmoth.device.v2`. Connecting is the take request; URL discovery alone does not request ownership. Closing is release; external clients have no separate take/release tool or HTTP mutation API. The sanitized, nonempty `client` and task `title` (up to 120 characters) are required; `reason` is optional context. Holder and queue snapshots carry `title` alongside the client name. The command protocol is version 2 so discovery refuses older services that do not retain leases on device loss. The wire/config mode names remain `takeover` (GizMoth control) and `piping` (exclusive WebSocket communication). Automatic approval defaults to true and works in either mode: requests wait for active jobs or preparation, then receive FIFO grants without persisting a mode change. Explicitly selecting `takeover` pauses automatic approval unless `autoGrant` is also specified. Queued sockets stay connected with `{"type":"queued","state":"pending","position":1,"holder":null}` and receive `{"type":"granted"}` on that same socket when eligible. A shared client name or API key cannot share the lease. The existing service-owned serial/H2Loader worker remains responsible for physical I/O and protocol handling throughout the grant; the client never receives the physical port or implements H2Loader.

Client commands are JSON text frames `{id,method,params}` with a unique request ID. `serial/ws.rs::commands()` defines strict parameter schemas for `send` (text and line ending), `install` (absolute local package path, optional stageOnly/jobId), `reboot` (app/loader target, optional jobId), `refresh` (optional jobId) and `cancel` (jobId). Raw text and binary client frames are rejected; binary server frames contain device logs. Every command receives `{type:"result",id,ok:true,result}` or `{type:"result",id,ok:false,error:{code,message}}`; pending errors additionally carry `state: pending` and preserve the connection and queue position. Commands execute only under the current socket lease and worker generation, including install, reboot, refresh and cancellation. Job progress/completion pushes `{type:"job",job}` on that same socket. Installation requires the actual connection to be local; LAN callers cannot submit local package paths, regardless of authentication or proxy headers. External HTTP mutations are refused; the desktop retains private App IPC for port management, approval/rejection and reclaiming control. UI sends/jobs cannot bypass an external holder, while cached status, logs and job queries remain available without a take.

Closing or revoking a socket cancels its session-owned work at safe I/O boundaries. The runtime withholds the next grant until completion/cancellation has settled, so a new client cannot interleave with the previous session's remaining I/O. After the automatic queue drains, GizMoth control resumes with its configured protocol. A protocol or baud-rate restart revokes an active holder explicitly and preserves waiting requests; changing communication ownership keeps the native protocol worker open. Physical unplug, read/open failures, protocol restarts, port disable and device re-enumeration preserve holder, waiters and task metadata. Explicit port removal and service shutdown end sessions. The application disconnects a selected session through its app-only `/v1/ports/{id}/connections/{connection}/disconnect` route; it validates that exact connection ID under the seat mutex before changing ownership or optional automatic-approval policy, so stale UI actions cannot disconnect a replacement holder. Legacy saved `mode: piping` values never reserve a device; actual ownership follows connected sockets. The desktop offers automatic approval and reclaiming control, without a mode switch for requesting ownership.

Physical availability uses a separate bounded broadcast of `device` events, not the queue/grant/end control watch. Events carry `sequence`, `at`, `state` (`disconnected`, `connecting`, `reconnecting`, `connected`), `connection`, `ready` and optional `reason`. This preserves a brief loss followed by recovery instead of coalescing it away. New sockets receive an initial snapshot after their initial queue/grant notice. Lagging consumers receive the current availability plus `missedEvents` without losing ownership. Retired worker generations cannot overwrite newer availability. Native reboot phases report reconnecting, while verified recovery reports connected on the same lease. Ownership authorization is independent of transport readiness: unavailable physical commands return 503 without buffering; cancellation remains allowed for the owner's existing job. Native I/O failure invalidates readiness before job completion/handoff, reopens the protocol worker and retains the holder. Previously recognized Auto H2Loader ports keep probing H2Loader across boot-time timeouts rather than silently falling back to plain serial; the operator can explicitly change the configured protocol when appropriate.

HTTP bodies are capped at 64 KiB with a five-second read deadline. Local and remote HTTP admission have independent 64-connection budgets; pipe admission has a separate shared 64-connection limit. Pipe frames/messages are capped at 64 KiB. Outgoing device logs coalesce adjacent callbacks into frames up to that limit, with a 256 KiB byte budget covering queued and in-flight data; the pinned H2Loader raw-log filter can emit one byte per callback, so callback count is not a slow-consumer signal. Byte-budget exhaustion explicitly revokes the holder without silently dropping logs, and a two-second send deadline ends a stalled socket. Device-write queues retain both message and byte budgets. Workers use bounded I/O with cancellation checks. Firmware jobs publish a queryable, cancellable `queued/preparing` job before expensive copying/inspection, return immediately, and revalidate authorization, socket lease, worker generation and cancellation before transfer. Desktop callers generate a UUID `jobId` before submission and preserve it in error messages; WebSocket install/reboot/refresh commands may supply one too. A repeated job ID is rejected for the daemon's lifetime, including after history eviction; deduplication does not survive a daemon restart. WebSocket jobs remain bound to the submitting socket, whose closure requests cancellation; they do not outlive that session without cancellation. After a lost response, inspect the port's current job and history before retrying; callers without a supplied ID locate the task through that snapshot. Blocking filesystem or native inspection calls check cancellation when they return, and a cancelled preparation cannot enqueue a transfer.

### Updates and MCP

Health and HTTP snapshots publish a persisted `instanceGeneration` across daemon restarts, independently of request timing or wall-clock changes. The daemon increments `serial/instance-generation.json` while holding its lifetime lock, before publishing an instance; corrupt, exhausted or unwritable generation state prevents startup. Desktop overview/watch replies additionally receive per-data-directory `ownerEpoch` and `observationEpoch` values from the main process after verifying the current discovery owner. PID, port and token are compared only in the backend; superseded connections cannot issue newer observations. `ownerEpoch` changes with the connection identity, while `observationEpoch` orders all verified online/offline reads. This keeps a busy legacy daemon visible after a modern daemon without accepting stale replies. Offline snapshots use instance generation zero and retain the last running version watermark for the same owner. Each snapshot request captures an observation watermark before discovery or HTTP I/O; publishing offline fences already in-flight running replies, including those from the unchanged owner. A fresh request can observe recovery normally. Health publishes `buildId` separately from protocol compatibility. The deterministic build fingerprint includes Rust/Cargo inputs, native sources/configuration and staged archive contents. App-only `POST /v1/retire` atomically refuses active/preparing jobs, external holders or queued requests with 409; an idle retirement closes admission and stops safely. Clients wait for discovery cleanup and the lifetime lock before starting the current executable. Discovery retries deferred migration once an already-running service becomes idle, without starting an intentionally stopped service. Legacy services lacking safe retirement require an explicit confirmed restart in Settings › Service. Updater preparation reserves serial readiness and retires the service before simulator shutdown. A separate `startup.lock` serializes ordinary cross-process discovery/startup with bounded waiting. An update reservation keeps `update.lock` held until cancellation or process exit, so ordinary contention is distinguished from an application update. Legacy binaries do not implement this barrier. Failed simulator preparation releases the reservation, and cancelling an update restores only a service that preparation actually stopped. Native E2E startup does not autostart resident services.

`gizmoth --mcp` provides global stdio MCP tools in `src-tauri/src/mcp/`, shared with `--tool` and `--list-tools`. The registry contains only `gizmoth_status`, `serial_list`, `serial_system_ports`, `serial_status`, `serial_logs`, `serial_job` and `serial_pipe`. These read-only queries call the daemon over HTTP, never open/enumerate ports themselves and never start a stopped service. Legacy mutation names fail with WebSocket guidance before service discovery, including against an older daemon; they have no HTTP fallback. `serial_system_ports` wraps the daemon's cached port array in an object. Exact IDs and paths take precedence over names; ambiguous names are rejected. `serial_job` budgets all polling against `waitSeconds` and follows the initial job ID through recent history, while zero reads the current job immediately. MCP requests use bounded concurrency and reserved protocol-control slots; device cancellation travels on the granted WebSocket. Incremental `serial_logs` calls must return the previous `instanceId` and `generation` with `after`; a missing or changed identity resets to the current tail. `serial_pipe` returns the advertised WS URL, bearer header, `protocol: gizmoth.device.v2` and the `commands()` schemas from `serial/ws.rs`. Discovery does not connect or request ownership; the agent holds the socket itself for commands and job events. The generated Skill teaches query → URL discovery → connect/wait → JSON commands/job events → disconnect. Its native renderer remains the source for `src/demo-agent-skill.json`. The browser fixture (`src/demo-serial.ts`, `?demo=1&empty`) follows the instance, log-generation and queue contract independently of the configured-port list.
