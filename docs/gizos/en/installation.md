# Installed applications and streaming installation

Host-side app directory and install behavior; packaging is distinct from successful runtime execution.

## Lua App catalog and streaming installation

`//libs/lua/apps:apps` owns an application catalog and installer independent of Lua Host and GizClaw. Its [API Reference](/references/lua-apps) comes directly from the production Public Header. Callers inject Memory, Filesystem and Sync, and configure `preinstalled_index` and a dedicated `install_root`. User KV must use a separate root outside the installation directory; user data must not be placed in installer-owned directories. FS may expose only a nested mount/view root. The installer searches upward from the target's parent for the nearest visible existing directory, then creates missing directories downward. It does not require stat/mkdir on invisible ancestors such as `/data` to succeed and does not widen the view. If parent stat proves that a location is a file, it returns a format error; other FS errors continue to fail unchanged. The catalog can survive Service reconnections. Before destroying it, stop and release Services and installation sessions that borrow it.

Preinstalled and remotely installed apps use the same format-1 Lua App manifest, `app_id` and version. `lua_app_index` generates `format=1, apps=[{root,manifest}]` from `LuaAppInfo.manifest`, without a handwritten version table. The rule's `installed_entry` output group supplies exactly the same original or compact Lua text as the package. `installed_files` includes that entry and original data files. Consumers map the entry to `<app_id>.lua` under the installation root and preserve the matching data subdirectory structure. Existing default archive/manifest/metadata release outputs are unchanged. Preinstalled entries with missing required files, mismatched file sizes or oversized entry points are excluded from listings at load time. An installed item overrides a preinstalled item with the same ID; each ID is listed only once.

The URL installation entry accepts only HTTP and HTTPS, at most 1024 bytes, and rejects data URLs. In-memory archives use incremental Binary input. HTTP requests do not retry automatically. Redirects remain restricted to HTTP(S), allowing relative addresses resolved by HTTP PAL. HTTP streams and incremental Binary inputs both use only fixed windows; the complete compressed archive is never written to disk. `libs/crypto/sha256` computes archive and per-file digests incrementally; version validation reuses `libs/semver`.

Incremental installation uses begin/write/finish/abort. One owner serializes calls for a given session. The session holds a catalog reservation; catalog operations from other tasks return BUSY, and the same owner must not reenter catalog operations. finish publishes only after declared length, optional compressed SHA-256, manifest, every file's length and SHA-256, complete USTAR end blocks and zlib EOS all pass. Default limits are 32 app identities, 64 payload files, a 256 KiB entry, 2 MiB payload per package and 8 MiB total installed payload. Preinstalled bytes do not count against installed-byte quota.

The installer first writes ordinal staging files, moves verified files into that ID's inactive slot, then publishes the overall index through replacing atomic rename. Before cleanup it checks manifest identities in both slots. If the filesystem maps different app_ids to the same directory, installation is rejected and published apps are preserved. Cancellation observed by the installer, input errors and publication failures preserve the old version and independent KV. Transport timeout does not prove the device did not install; query the listing after reconnection rather than automatically retrying installation. After successful publication, old-slot cleanup cannot report the completed installation as failed. Filesystem must provide synchronous writes and replacing atomic rename. If a close error leaves it impossible to establish whether the handle was consumed, the catalog enters a terminal storage-error state, retaining itself and borrowed dependencies. It must not automatically retry close or release a possibly live backend; recovery requires ending the process or device lifecycle.

`h2_lua_apps_uninstall` idempotently uninstalls by stable `app_id`, preserving independent user storage. It first atomically publishes catalog removal, then cleans both writable version slots according to their manifests. Publication failure preserves the old app; cleanup failure after publication leaves it unavailable, and repeated uninstall retries cleanup. Preinstalled files are immutable. The catalog uses `{"app_id":"demo","removed":true}` to persistently hide the preinstalled identity and its override, so restart does not restore it. Reinstalling the same ID restores normal listing. Remote-only identities are removed from the index, freeing app-count and byte budgets. Read-only catalogs do not advertise uninstall support. The running owner must coordinate jobs still using entry/data_dir snapshots.

`h2_lua_apps_get` returns caller-owned entry/data_dir snapshots for the product owner to submit to Lua Host through its own execution flow. The installer neither starts a VM nor changes product UI. The running owner should coordinate app updates; installation paths in snapshots are not retained permanently after subsequent updates.

Host may configure `on_display_present` to observe the complete RGB565 framebuffer after the Display worker successfully finishes PAL present. Pixels and callback context have explicit borrowed lifetimes. The callback must neither retain pixels nor reenter Host. It can support digest/golden validation, proving only that the renderer and PAL accepted the frame, not the panel's optical output.
