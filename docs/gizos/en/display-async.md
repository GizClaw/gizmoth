# Asynchronous Display submission

Single in-flight submit, flush, status and busy handling for frame loops.

## Single-in-flight Display submission prototype

Display on every target, including Web, uses the common display worker, without a synchronous backend mode or enable switch. The first `require("display")` acquisition creates a `$lua/display` task. Jobs that do not use Display create no display task. `present/end_frame` still wait for the current frame to complete; `submit/flush/status` provide single-in-flight asynchronous submission. `h2_lua_display.h` defines the complete contract.

The default `//libs/lua` / `:lua_runtime` task inventory contains `$lua/worker` and `$lua/display`; the lower Runtime's existing task inventory is unchanged. Consuming targets must configure core, priority, stack and memory region for `$lua/display`, or explicitly specify `default` after reviewing the budget. Existing task-policy audit still rejects missing policies. The source package contains the same implementation. Non-Bazel embedders supply PAL Task, Sync semaphore, Time and Display, and own their task budgets. A zero-initialized Host configuration supports the worker; `display_worker_stack_size` adjusts only the stack budget.

Host supports multiple Jobs, but only one Job may acquire Display at a time; competing acquisition returns busy. After successful `deinit` or checked release, another Job may acquire it. This ownership guard cannot coordinate other Hosts, Runtimes or direct PAL/UI writers. Callers must drain and pause those external accesses first. Backends must allow serial handoff to one task, and successful draw/present must complete transfer. open/info/draw/present/close execute on the same submission task. `borrow_display` retains its contract of not calling PAL open/close.

Display holds only two full-screen RGB565 pixel buffers: Lua drawing buffer A and worker send buffer B. Before publication, planning compares A with the last successful B. The worker first copies A to B according to the final plan, preserving original row stride, then publishes completed copy handoff and sends B through PAL. `submit` waits for that copy handoff; Lua can then continue drawing A in parallel with B's transfer, without waiting for transfer completion. Reentrant submission from a finalizer during initial send-buffer allocation returns busy, preventing allocation of another full-screen B. OOM clears this preparation guard before raising an error, so releasing other memory allows a normal retry. After complete successful transfer, B directly serves as the retained baseline. Completion acknowledgement neither copies the whole frame again nor clears next-frame dirty state. The first frame or an invalid baseline still copies the full frame; unchanged frames copy no pixels. There is no third full-screen snapshot. The complete tile map is traversed separately during copying and transfer; exceeding rectangle capacity does not truncate it.

At most one frame may be unfinished, including copy and transfer phases. Lua callers handle busy by retrying after `runtime.sleep()`; no extra frames are queued. Send buffer B, mailbox and bounded plan use VM userdata, constrained by `vm_memory_limit_bytes` and the shared VM heap. Two 240×240 RGB565 buffers total 230400 bytes: acquisition allocates A through the Host allocator, and the first submission, including `present`, adds just one VM-charged 115200-byte B plus metadata. This excludes application-created background/region caches and driver-owned DMA buffers. PAL Task/Atomic/Sync internals belong to platform budgets, not VM charges. `display_worker_stack_size` requests 8192 bytes by default; actual stacks also obey target-policy minimums. The new `$lua/display` task must declare core, priority, stack and memory region in the consuming target's task policy. Measure total peak use and contiguous free blocks on the target. The library does not change drivers, SDKs or compiler arguments.

`deinit`, job release and Host join return busy while frame transfer remains unfinished, retaining VM references and ownership for later retry. Close requests execute through the same worker. PAL join may then wait for exit or return busy; only success releases ownership and buffers. `h2_lua_host_destroy_checked()` releases Host only on success. After failure, Runtime must not be destroyed and a UI borrowing Display must not resume. The compatible void destroy also preserves failed objects, but callers must use the checked entry point to determine whether release completed. PAL errors are latched and stop new submissions. A wakeup or copy-handoff wait failure does not establish that the worker has stopped reading A, so drawing is also frozen and both buffers retained. Once the submission task exits, it may be joined, but uncertain device state never triggers automatic close/open or retry. This prototype has no API to lift fault isolation: after a fault, Host/VM/device leases remain held. Consumers must maintain dependencies and use external recovery or process restart. Infinite PAL waits may prevent synchronous calls or tasks from exiting. Software busy does not mean hardware is cancelled; forcibly deleting a task and then freeing resources is invalid.

Frame rate is calculated only from successful completion records with changed pixels. submitted, unchanged submits and failures cannot count toward changed-frame FPS. Times are PAL monotonic transport completion times, not panel scanout; Web transfer completion also does not prove browser composition onto the screen. Observers must not concurrently read ordinary 64-bit fields while the worker updates them; consume completion records published through `status/flush`. The checked-in shared consumer example is `libs/lua/tests/display_submit.lua`, run by both native worker tests and browser tests for `projects/example/targets/pkg_tar/lua-script-submit`.

Host regressions can directly compile the production catalog, GizClaw handler and Desktop PAL to test package validation, uninstall, persistence, fault recovery and streams:

```sh
python3 libs/lua/apps/tests/run_host_tests.py --yyjson-dir /path/to/yyjson/src --gizclaw-dir /path/to/gizclaw --sanitize
```

The `gizclaw` checkout should contain the generated C contract and initialized pinned nanopb submodule. This validation uses Host PAL; device Golden E2E separately verifies downloading, display and product-task lifecycles.

Public regression `//libs/lua/apps/web/tests/scoped_http:browser_test` downloads and installs format-1 packages through real Web FS and HTTP, runs Lua across two reloads, and verifies independent KV and storage files remain after uninstall. An independent Bzlmod consumer runs the same target.
