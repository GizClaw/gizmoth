# Display drawing and frames

Graphics, colors, shapes, retained drawing and frame submission. See input-example for basic drawing.

### Display AA and framebuffer fade

`display.fill_circle_aa(cx, cy, radius, color)` blends into the RGB565 framebuffer using bounded supersample coverage; `radius` is restricted to `0..64`. `display.fade_to_black(amount)` fades the entire framebuffer. `display.fade_rect_to_black(x, y, width, height, amount)` fades only a positive-size rectangle entirely inside the framebuffer. Both accept `amount` in `0..255`. All three mark only the dirty region remaining after clipping and do not implicitly `present`. Fades smaller than one RGB565 channel step use a fixed, bounded spatial phase so dark trails eventually disappear even at high FPS.

`display.draw_circle(cx, cy, radius, color)` draws a one-pixel circumference clipped to the framebuffer. The center may range from one negative Display width/height to twice the positive width/height; radius must be in `0..min(display.width, display.height)`. Out-of-range values, a closed Display or an invalid color fail deterministically under the existing Lua argument/error contract. `clear`, rectangles, circles and rounded rectangles can write framebuffer pixels in batches. By default, `present` submits the dirty bounding union of all pending primitives; the retained comparison mode below can be enabled explicitly.

### Display polygons, ellipses and retained commands

`display.fill_polygon(points, color, offset_x=0, top=0, bottom=height, scale=1)` accepts 3..128 `{x,y}` points. Coordinates and horizontal offset must be finite and within ±100000; scale is `0<scale<=16`. Vertices are scaled first, then scan-converted on integer rows using the even-odd rule. Edge vertical ranges are lower-inclusive and upper-exclusive. Each intersection pair covers `ceil(left)..floor(right)`, including both horizontal endpoints. Horizontal offset is added as `floor(value+0.5)` only after intersection rounding; this differs from translating vertices during transformation. Concave polygons, self-intersections, repeated points and degenerate edges are supported; the latter two do not cause division by zero.

`display.fill_ellipse(cx, cy, rx, ry, color, offset_x=0, top=0, bottom=height)` uses the same coordinate range and requires `rx>=0` and `0<ry<=2048`. Local y advances from `-ry` to `+ry` in steps of 1. The destination row is `floor(cy+y+0.5)` and half-width is `rx*sqrt(max(0,1-y*y/(ry*ry)))`. The left endpoint is `floor(cx-half_width+offset_x+0.5)` and width is `floor(2*half_width+1.5)`. Fractional radii retain this pixel-sampling rule; they do not implicitly scale the framebuffer.

`display.compile_commands(commands)` copies at most 16384 six-field commands into immutable VM-owned userdata. `{0,x,y,width,height,color}` represents a rectangle; `{1,x,y,x2,y2,color}` represents a line segment. Kind must be an integer. The four numeric fields must be finite and within ±100000, and are truncated toward zero to pixel integers. Rectangle dimensions cannot be negative. Empty lists are valid. Modifying or releasing the original table after compilation does not affect commands. Keeping the userdata referenced preserves it across GC; releasing its last reference allows collection. The copy counts against the job's VM memory budget, creates no system-heap cache and does not grow automatically.

`display.draw_commands(handle, top=0, bottom=height, offset_x=0, offset_y=0, scale_x=1, scale_y=scale_x, color_override=nil)` replays commands in their original order. Offsets must be finite and within ±100000; both scales must satisfy `0<scale<=1000`. Endpoints are computed as `floor(offset+coordinate*scale+0.5)`. Rectangles use half-open intervals; lines are clipped before Bresenham iteration, so distant off-screen endpoints do not produce raster loops proportional to their distance. Color overrides do not modify original commands. Colors follow the Display string or `{r,g,b}` contract: `green` is RGB(0,128,0); full-brightness green requires explicit RGB(0,255,0).

These drawing operations clip rows to `[top,bottom)` and columns to the framebuffer. They require integers `0<=top<=bottom<=height`, checked before conversion to native int. Empty clips and zero-area rectangles do not modify pixels. Drawing starts only after all arguments are decoded. Invalid arguments or a closed Display raise a Lua error. RGB table getters still follow Lua metamethod semantics; their own side effects are outside drawing's atomicity guarantee. Failed compilation returns no partial handle. After OOM, releasing temporary data allows retrying a smaller batch. Drawing only marks the dirty union and does not implicitly present. Retained commands do not hold the framebuffer after Display deinit and cannot continue drawing. Repeatedly calling cached `require('display')` does not reopen the device.

### Display indexed rectangles and palettes

`display.compile_rects(records)` copies named `{x,y,width,height,color_index}` records into immutable userdata. `display.compile_palette(colors)` converts existing color strings or named `{r=...,g=...,b=...}` values into fixed-length RGB565 userdata. Both accept at most 16384 entries; empty lists are valid and data counts against the VM. Existing commands/mesh interfaces are unchanged. Lua color indices start at 1, and drawing validates them against the actual palette length.

`display.blend_palette(output,a,b,progress)` requires three equal-length palettes and integer progress in `0..256`; output may alias an input. `display.draw_rects(batch,palette[,left,top,right,bottom])` uses an already-open Display. Either supply all four half-open clip integers or omit all four. Success returns no values. The call does not implicitly present, grow capacity or allocate memory. See the [Lua API](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/references/lua.md) and [Raster2D](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/zh/developing/raster2d.md) for the full argument and pixel contract.

The C core validates everything before drawing; the adapter then marks existing dirty/background damage rectangle by rectangle. There are no new caches or damage objects. Construction and palette blending do not open Display. `require('display')` retains existing acquisition behavior; a closed proxy cannot draw. Argument getters may have side effects. Construction does not write the framebuffer, and later drawing must recheck Display state. GC, cancellation, job release and Host teardown retain existing reclamation paths.

### Display quad strip batches

`display.compile_quad_batch` stores caller-defined normalized strips, optional horizontal patches and painter order. Each `display.draw_quad_batch` call accepts four corners, colors and optional row clipping, reusing existing polygon rasterization, dirty/background damage and retained present. See [Display API](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/references/lua.md) for interfaces and exact interpolation order. Colors may use existing `compile_palette`, or a reusable ordinary Lua color array to update RGB888 formulas each frame. The batch does not generate gradients or glow colors, or choose viewpoint, topology or visibility.

Optional trailing `clip_top/clip_bottom` arguments specify a half-open integer row interval in the framebuffer. Omitted or `nil` values use `0/height`, respectively, with `0<=clip_top<=clip_bottom<=height`. They limit raster scan rows only: they neither move corners nor reinterpolate, and are independent of normalized patch `top/bottom` in batch records. Empty clips still fully validate colors, corners, intervals and Display acquisition. Drawing multiple disjoint intervals with the same painter order on each row can reproduce the full image. Each call still decodes colors and expands geometry; applications choose dirty row intervals. This interface adds no scan-span cache.

Topology is limited to 256 entries, copied at initialization into VM-charged userdata and reclaimed by GC/VM teardown. No mesh, intermediate vertex buffer or raster cache is created per frame. Explicit horizontal patches are interpolated first, then strips expand along both sides, preserving the floating-point operation order and draw order of individual Lua `fill_polygon` calls. A successful draw allocates no storage; all colors and corners are validated before the first pixel write. Empty batches, degenerate strips, overlap and screen clipping follow polygon behavior. Lua side effects in color getters are outside the failure-atomicity guarantee.

### Experimental Display dual-rail material batches

`display.material_strip` accepts two caller-supplied screen XY rails and reuses an f64 buffer, compiled material and palette. See [Display API](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/references/lua.md) for the public contract. Geometry updates with the same station count preserve bindings; changing the station count releases old bindings. Each face retains material → iso-line order, using the existing Q24, complete fallback and integer line phase. This candidate does not choose projection, topology, visibility, color formulas or submission timing. Before integration, compare against scalar and Lua shared-endpoint baselines, measuring actual geometry upload, binding, palette update and cold/hot drawing costs. The consuming application should decide on its target device whether to retain it.

Dynamic colors for different faces in one batch require separate mutable palettes. Reusing one palette and then drawing the batch makes all references read the same final color. Successful load/bind/draw operations allocate nothing after reserving Lua stack space and create no mesh or raster cache. Storage and binding references are charged to and reclaimed by the VM. Construction, OOM, finalizer reentrancy and full validation before the first pixel write follow the public header contract.

### Display strokes and bounded caches

`display.stroke_path(points,widths,color,offset_x=0,top=0,bottom=height,cache=false,fast=false,smooth=false,scale=1,tolerance=0)` accepts `2..256` finite point pairs within ±100000, exactly `n-1` widths in `0..1000`, and either one color or `n-1` colors. cache/fast/smooth must be booleans. Scale is `0<scale<=16` and applies first to coordinates and widths. Offset must be finite and within ±100000. top/bottom use the existing on-screen half-open integer row clip. All arguments, color getters and allocations complete before drawing, followed by a Display recheck. The return value is `(cache_hit,fast_segment_count)`, not frame rate.

The first argument may also be `{buffer=xy,count=n}`, where xy is an f64 packed xy buffer with capacity at least `2*n`, n is an integer in `2..256`, and coordinates retain the finite ±100000 limit. The descriptor must not mix in a numeric-key point array. Fields use raw reads; each call copies and validates current coordinates before drawing. A stable descriptor table holds the existing normals cache, and the widths table holds the existing span cache. Coordinate, count or style changes invalidate them; comparing buffer identity alone is insufficient. Other arguments, return values, pixel algorithms and explicit present behavior are unchanged. The buffer stays alive throughout the call, Display lifecycle is still checked after color getters/GC, and raw pointers are not retained between calls.

Default hard mode uses a width-centered quad and centerline for each segment; lengths below `.01` draw a rounded-to-integer square. Nondegenerate zero-width segments retain the centerline. fast uses float/FMA quads with integer-boundary error checks, falling back to double-precision geometry when conditions are not met. The width-independent double-precision normals cache lives with the point table and compares all coordinates. cache retains at most 2048 ordered scan-span/centerline records with the widths table; its key includes scaled coordinates, widths, colors, offset, clip, viewport and mode. Insufficient capacity still draws the complete result but invalidates the cache; it must not truncate the image. Both cache types count against the VM, can be collected after releasing point/width tables and do not hold the framebuffer.

smooth explicitly enables continuous coverage with round caps. Each pixel blends only its maximum alpha once; equal alpha preserves the earlier segment's color, and zero widths are skipped. Pixel centers are `(x+.5,y+.5)`. Coverage is `clamp(radius+.5-distance,0,1)`, rounded to `0..255` and blended using existing RGB565 blending. Endpoint ranges up to 4096 retain screen-local float fast coverage; extreme coordinates use a double-precision fallback. This does not promise identical pixels to hard mode. Color/coverage scratch is allocated for the clip region, reused within a job and dereferenced when Display/job/Host closes. tolerance is a screen-pixel chord error in `0..0.25`, disabled by default and used only for smooth. It preserves style boundaries, rejects foldbacks and checks every omitted point without changing world physics nodes or time steps.

For smooth, `cache=true` enables a coverage cache for single-color strokes with `tolerance=0`. A stable widths table holds one VM userdata with at most 16 KiB of payload. Its key includes point count, scaled coordinates/widths, scale, exact offset, row clip and viewport. Color and background are excluded: a hit blends the current color into the current framebuffer, preserving per-stroke glow/fill order. It stores only quantized alpha, not RGB565 background. Multicolor, simplification, empty ranges or over-limit inputs retain their original paths and existing caches. Hot hits allocate nothing and return `(true,0)`; cold draws/fallbacks return `(false,0)`. Releasing widths permits GC. Cold-build staging and job scratch both count against the VM quota. Allocation failure publishes neither an incomplete cache nor this call's pixels. See [Lua Display API](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/references/lua.md) for detailed lifecycle, invalidation and memory contracts.

General polygons use float edge-slope/integer-boundary checks, falling back to the original double-precision intersection expression when identical floor/ceil results cannot be established. Reference pixel tests cover boundaries and deterministic random input; finite samples are not treated as mathematical proof. Strokes consume one shared set of numeric helpers through Utils' public `h2_f32_math.h`. See [Utils](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/zh/developing/utils.md) for compiler and floating-point environment constraints. Do not enable fast-math for drawing or physics libraries.

### Display snapshots, background restoration and retained submission

`display.region_from_string(width,height,data,encoding="rgb565be")` creates an opaque region directly from a Lua string. Width and height must be integers in `1..4096`. The constructor itself does not acquire Display: resources can still be created after calling `deinit` on an acquired proxy, without drawing or implicitly presenting. The first `require('display')` retains the existing acquisition contract and raises an error if acquisition fails. Cached require does not reopen the device; drawing after closure still fails. In a valid drawing session, the result can be passed to `draw_region`, and a screen-sized result to `restore_background`. Applications own pixel data and call timing; the function does not read files or preload resources.

Default `rgb565be` accepts exactly `width*height*2` binary bytes in row order, with each RGB565 pixel's high byte first. `rgb565be-lz4-b85` accepts an 8-digit ASCII hexadecimal compressed length followed by Python `base64.b85encode(block,pad=True)` text. The block is standard raw LZ4, without a frame or additional output dimensions; output must match width and height exactly. Base85 characters, text length, 32-bit group overflow, zero padding, LZ4 truncation, offsets, output bounds and final-sequence conditions are all validated; trailing extra data is rejected. See [Lua Display API](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/references/lua.md#regions-from-strings) for the full encoding contract and examples.

Synchronous decoding writes directly into region userdata on the owning VM worker, without constructing a Lua pixel table or full intermediate decompression buffer. Base85 groups are decoded individually by [`libs/encoding`](https://github.com/GizClaw/gizos/blob/81e8cbfc64760b5bcc89e8be771393662e876ea5/guides/zh/developing/encoding.md)'s `h2_encoding_decode_base85_group()` using the read-only `h2_encoding_base85_rfc1924` decoding table. Display still validates length headers, complete groups, zero padding and LZ4 rules. Pixels, row metadata and damage tiles count against the VM quota. The input string uses its own quota while alive, but the region does not retain it. Invalid input raises a Lua error; quota exhaustion uses the normal Lua memory error. Failure publishes no partial region and leaves the framebuffer unchanged. Temporary userdata can be collected, and releasing other data permits retry. Ordinary regions are reclaimed after their last reference is released; background-held regions follow `release_background` and teardown release rules.

`display.capture_region(x,y,width,height,key=nil,reuse=nil)` captures a positive-size framebuffer region. Width and height are each at most 4096; position and dimensions must be integers and entirely on-screen. It stores only already-drawn RGB565 pixels and does not load textures or files. Omitting key captures an opaque region; supplying key compresses transparent margins on each row and precompiles nontransparent runs. Transparent capture first counts, then allocates the final VM userdata directly. Allocation may run finalizers, so it revalidates Display and region bounds, then checks capacity and copies pixels from the current framebuffer and stride in an allocation-free scan. Key-colored pixels between each row's first and last pixels remain stored; ordinary replay and replay with different keys retain their semantics. If a finalizer changes the required pixel or run count, the unpublished result is discarded and the operation falls back once to a complete VM snapshot before compression. It neither keeps framebuffer pointers across allocation nor retries indefinitely. Side effects from finalizers drawing or reopening Display remain; closing Display or shrinking it below the region size raises an error. Capture itself does not draw, OOM publishes no partial result, and all temporary/final storage counts against the VM quota. reuse requires matching dimensions and transparency mode; transparent snapshots also require the same RGB565 key, otherwise an error is raised. Opaque reuse, or transparent reuse with enough pixel and run capacity, updates in place through an allocation-free scan without finalizer callbacks and returns the same userdata. All aliases observe new content; capacity does not shrink with content. Insufficient transparent capacity takes the ordinary allocation path above and returns a new snapshot, leaving the old one unchanged. OOM also preserves old content, except for explicit changes by user finalizers. Callers must retain the returned value. The public layer does not create cache pools or reserve extra capacity automatically. `display.masked_region_reuse == true` indicates support for this contract; older modules omit the field. Like width/height, it is informational: changing the Lua field does not toggle native support. Recapturing the current opaque background invalidates the restoration baseline; the next restoration is complete.

`display.draw_region(region,x=0,y=0,top=0,bottom=height,key=nil,left=0,right=width)` replays at native pixel size without scaling. Integer x/y range is ±100000. Integer clip boundaries form an on-screen half-open rectangle. Omitting key means opaque replay, including restoration of margin colors omitted during compression. A different replay key also reconstructs captured content correctly. A replay key matching the capture key directly copies precompiled runs. Empty clips write no pixels. Device state is checked after color getters complete; invalid arguments cause no drawing writes, while getter side effects remain Lua behavior.

`display.restore_background(region)` accepts only a full-screen opaque snapshot and retains a VM reference. Initial binding or an invalid restoration baseline triggers a full copy. Subsequent calls combine 16×16 dirty tiles marked by all drawing operations into adjacent row spans, restore only those regions, then clear background damage marks. Background restoration and previous-frame submission are independent state: “submitted” does not mean “restored.” `display.release_background()` releases the reference idempotently. The snapshot remains replayable and is collected after its last reference is released.

`display.present(options=nil)` and `end_frame(options=nil)` return the actual submitted `(pixel_count, rectangle_count)`. options is an ordinary table whose fields use raw lookup. `retained` is boolean, explicitly enabling or disabling comparison with the last successful frame; omission preserves the current mode. `bounds` is boolean and combines this call's submission into one bounding rectangle. `merge_gap` is an integer in `0..8`, limiting unchanged tiles crossed by local span/tile merges, still measured on a 16-pixel grid. This is a local merge limit, not a promise to merge; automatic bounding-box/full-screen candidates are exempt. The first retained frame, or the first after invalidation, submits in full. Later calls finish pixel comparison and region planning within the dirty range before submitting changed regions; a completely static frame returns `(0,0)`. `tiles=true` explicitly skips fine span planning, compares 16×16 tiles exactly, then uses existing `merge_gap` and guard merging. Omission or false keeps the default. This option affects only retained planning for the current call, trading potentially more submitted pixels for less planning CPU without guaranteeing a shorter total completion time. `bounds=true` retains the original tile-aligned bounding rectangle. Default planning may return tighter pixel bounds; callers must not depend on a fixed tile size or rectangle count. PAL present is called and its errors propagated even when no pixels change. Any draw/present failure invalidates the submission baseline and follows the worker contract: stop new submissions and retain faulted resources. Partially successful rectangles do not constitute a successful complete frame. Switching retained mode submits one full frame, then uses the corresponding comparison or dirty-union plan. Send buffer B remains until Display is successfully released. These statistics measure software submission volume, not device FPS.

Snapshots, background damage marks, retained comparison maps, rectangle-planning scratch and baseline pixels all count against VM memory; the original working framebuffer remains PAL-owned. Lua deinit, job release and Host teardown disconnect all display cache references before releasing the framebuffer or running VM finalizers. Display cannot reopen during teardown; normal deinit makes drawing through the old proxy fail. OOM returns no partial snapshot; releasing other VM data allows retry. Existing snapshots remain valid if another capture fails.

Default retained planning first extracts continuous changed spans per row, connects adjacent rows with a growth limit of at most 16 extra pixels, and performs a bounded merge of existing rectangles every 16 rows. Span generation uses the internal heuristic `area + 256 × rectangle_count + 32 × sum(ceil(rectangle_height / 16))`: at most 128 rectangles, 4096 raw spans and 65536 rectangle-merge checks. Vertical connection checks at most 128 existing rectangles per span. Reaching a limit, or finding at least 56 changed points in an 8×8 sample, falls back completely to existing tile comparison and merging. Sampling must never omit changed pixels that need submission.

After the original plan completes, its rectangles are traversed once to accumulate submitted area, estimated block count and bounding box. The automatic guard uses an empirical cost range equivalent to `222..286` pixels per block. Let `ΔP` be bounding-box area minus the original plan's accumulated area, and `ΔB` be the bounding box's `ceil(height/16)` minus the original plan's accumulated block count. It replaces the plan with the bounding box only if `ΔP + k × ΔB < 0` holds throughout that range; ties retain the original plan. The implementation checks only the worst endpoint, uses no floating point and does not count fewer PAL calls as a benefit. The range is the outward-rounded ratio of empirical intervals of approximately `160..200 µs/block` and `0.70..0.72 µs/pixel`. It is a candidate sensitivity range, not a statistical confidence interval or PAL guarantee. Different backends' pixel conversion, window setup, block heights and waiting strategies can fall outside it. Conservative comparison guarantees neither better performance on every backend nor reduced total present time.

The original span or complete tile plan remains the baseline; another candidate exhausting its work budget does not discard it. The guard neither compares the framebuffer again nor changes the original plan's pixel coverage or failure semantics. Tile fallback has no 128-rectangle submission limit. If scratch capacity is exceeded and the guard rejects the bounding box, it replays the complete original plan from the existing tile byte map, without submitting a partial prefix or forcing larger area. Original tile pixel comparison runs only when original span planning fails. Replay after capacity overflow traverses only marks; its extra cost still needs target-device measurement. `bounds=true` directly uses the original tile-aligned bounding box.

Rectangle storage and counts occupy 1028 bytes, allocated once with the VM-charged worker mailbox. The end of send buffer B stores one comparison/traversal byte per tile. The existing comparison byte per tile retains damage and traversal bits. The guard's area, block and bounding-box summaries use only fixed-size stack variables, adding no resident cache or per-frame allocation. Hot present allocates nothing and keeps no extra native-heap cache. After successful Display release it follows VM GC lifetime. Once planning completes, the Display worker copies and calls PAL. The send buffer also serves as the tentative baseline, valid only after the entire PAL present succeeds; failures follow the submission task's fault-isolation contract.

#### Submission planning validation

From the repository root, run `bazel test --config=macos_arm64 //libs/lua:all` (use the appropriate config on Linux). `display_plan_test` compares with the original tile merge rules using moving hollow diamonds, translated rectangles, sparse noise, dense frames, unchanged frames and alternating checkerboards. It replays submission rectangles over the old framebuffer and checks final pixels individually. It also covers random dirty boxes, odd sizes, 4096-axis boundaries, capacity exhaustion, complete 256-rectangle fallback, explicit bounds, guard rejection/ties preserving the original plan, and 64-bit area accumulation. Both endpoints of the empirical cost range are checked to be no worse than the complete original plan for the same frame. `lua_test` uses real Lua present/PAL fakes to check first frames, clearing old positions, successful guards, complete fallback, allocation-free hot paths and VM charging/release of the single send buffer. A separate fault suite checks resource isolation after partial draw failures, present failures, static-frame failures and failures midway through fallback exceeding capacity. Source-package tests verify export of the planner with the portable runtime.

Run `bazel-bin/libs/lua/display_plan_test` directly for generic synthetic comparisons. Optional `--frames <path> [first last]` reads local consecutive 240×240 full frames with no header in RGB565 big-endian format. Frame numbers start at 1; preceding frames still establish the baseline. This entry point is for offline validation, not a Lua/PAL API. Do not commit private traces to the public repository. Timing samples the mean of 10 planning runs for the same frame, then reports p50/p95/max. It includes only diffing and planning, including fallback; it excludes drawing, baseline copy, PAL submission and actual bus waiting. Comparisons consistently use full-screen dirty candidates and `merge_gap=1`, which may differ from dirty/options supplied by consumers. Static synthetic scenes still compare the full screen; an actual present with no dirty region skips planning directly.

Synthetic output compares three plans: original `tiles`, default `selected` and explicit `direct-tiles`. `fallback` counts frames taking the complete tile path after original span planning fails. Pixel replay and cost constraints compare against the complete span/tile baseline before the guard, for the same frame and dirty/options. `direct-tiles` validates final frames through pixel replay and checks guard cost against the same frame's complete original tile plan; it need not outperform default fine span planning. The postprocessing guard may cross local `merge_gap`, but must pass strict benefit checks over the entire empirical range. The retained original plan may still not be the model's global optimum.

Fewer pixels may mean more windows and higher planning costs. Host timing or submitted area cannot be converted directly into MCU FPS. Consumers should measure the target device's planner, fixed per-window/block cost, baseline copy and actual transfer time before deciding whether to retain the current cost weights. Frame rates are not promised without device validation. Algorithm references are [fbcp-ili9341 exact scanline diff and span merge](https://github.com/juj/fbcp-ili9341/blob/master/diff.cpp) and [LVGL lv_refr_join_area](https://github.com/lvgl/lvgl/blob/v9.2.2/src/core/lv_refr.c), both declaring MIT licenses ([fbcp](https://github.com/juj/fbcp-ili9341/blob/master/LICENSE.txt), [LVGL](https://github.com/lvgl/lvgl/blob/v9.2.2/LICENCE.txt)). This bounded planner is independently implemented and imports neither their platform code nor dependencies.

### Display retained geometry and native updates

`display.compile_mesh(vertices, primitives, vertex_capacity=#vertices, primitive_capacity=#primitives)` creates VM-owned retained geometry. `display.update_mesh(handle, vertices, primitives)` replaces all active data within fixed capacities. Vertices are `{x,y}` and primitives are `{kind,first,count,color}`. Kind 0 is a 3..128-vertex polygon; kind 1 is a two-vertex line segment. Lua first starts at 1; overlapping contiguous vertex ranges are allowed. Limits are 65536 vertices and 4096 primitives. Coordinates must be finite and within ±1000000. Empty data and zero capacities are valid. Lua updates first decode completely into VM temporary storage, so any later argument error cannot leave a partially applied update. Success replaces active lengths, topology and colors, invalidating derived coordinates. Caller color getters' side effects still follow Lua semantics.

`display.draw_mesh(handle, options=nil)` draws in original order. options fields use raw lookup; defaults do not come from metatables:

| Field | Contract |
| --- | --- |
| `matrix` | `{a,b,c,d,tx,ty}`, identity by default; computes `x'=(a*x+c*y)+tx`, `y'=(b*x+d*y)+ty`; fields finite and within ±1000000 |
| `transform` | Optional `{x=...,y=...,scale=...,angle=...}`; all four fields required and raw-read; mutually exclusive with explicit matrix. x/y/angle finite within ±100000, `0<scale<=100`; grid in 1..16 must be supplied explicitly |
| `grid` | On matrix path, integer 0..16, default 0 means no snapping; nonzero snaps transformed vertices with `floor(value/grid+0.5)*grid`. On transform path, required integer 1..16; application chooses policy |
| `offset_x` | Finite within ±100000, default 0; polygons shift horizontally after intersection rounding, lines before continuous clipping; not combined with matrix translation |
| `left,top,right,bottom` | Integer half-open clip rectangle, full framebuffer by default, entirely inside framebuffer; empty rectangles valid |
| `color` | Optional Display color override; retained colors unchanged |
| `cache` | Boolean, default false; retains ordered scan-span/line records as needed, at most 8192; initially 16..512, grows as needed and shrinks to actual count after replay |

Before rasterization, all derived vertices are validated as finite and within ±16000000. Polygons use the even-odd scan and intersection rounding rules above. Lines are continuously clipped, then rounded with `floor(endpoint+0.5)` and drawn with Bresenham. Drawing does not implicitly present and is rejected after Display closes. Content updates, matrix/transform and grid invalidate the derived-vertex cache. Clip, color and offset apply on every draw and cannot be skipped on a coordinate-cache hit. The optional span cache also compares clip, viewport, offset and recolor; hits replay in original order and mark dirty/background damage. Capacity overflow still draws completely but publishes no partial cache. Successful native/Lua updates require derived-coordinate revalidation but preserve the previous successful draw's span candidate. Reuse is allowed only after full validation confirms identical active vertex/primitive counts, primitive kinds/ranges/colors, final coordinates and drawing parameters above; addresses or bounding boxes alone are insufficient. Consecutive updates, failed calls and draws without cache retention do not overwrite the candidate snapshot; hot calls with identical inputs reuse validated comparison results. When first enabling the cache with an identity transform, a conservative bound sums each polygon's clipped integer row count times `floor(edge_count/2)` plus one record per line, with initial capacity restricted to 16..512. At most 128 polygon vertices are examined; reaching the budget or bound retains 512 records, as do other transforms. A vertex/primitive snapshot plus aligned/fixed metadata is also allocated according to declared capacities. Estimation only hints allocation; if finalizers change mesh or viewport during allocation, original validation and overflow handling still apply. If one rasterization exceeds capacity, the frame still draws completely without publishing a cache. The next draw replaces the cache at entry with 4× capacity, capped at 8192 records. After at least one replay, at least 256 unused slots cause the next draw to replace it at entry with a cache sized exactly for existing records, copying records and snapshot. If that shrunken cache overflows, it returns directly to 8192 records and never shrinks again, preventing repeated allocation for animated meshes. Growth, shrinkage and restoration allocate only at entry. If finalizer reentrancy changes the cache during allocation, replacement is abandoned and the reentrant result retained. Subsequent hot draws allocate nothing. Data and caches count against the VM and are reclaimed by GC or VM teardown after references are released.

Explicit transform preserves the operation order of `(x+(vx*cos(angle)-vy*sin(angle))*scale)/grid` and its y counterpart, without premultiplying into an affine matrix. Trigonometric results are reused when arguments are unchanged. Each axis uses the original float expression with a `64*FLT_EPSILON` error bound: float rounding is used away from half-grid boundaries when error is below 0.25, otherwise the original double expression is used. Source vertices outside ±100000 also fall back. Applications choose grid, pose, layout and reuse timing; the library adds no size threshold or extra output scaling.

With an exact identity matrix and `grid=0`, drawing reads mesh-owned vertices already validated at creation/update directly. It neither copies them into a derived-coordinate cache nor recomputes identity transforms per vertex, and does not borrow caller buffers. Existing derived-coordinate storage remains available for general transforms, without additional capacity or allocation. This fast path uses no approximate comparison. Nonidentity matrices or nonzero grid still fully validate transformed results before modifying coordinate caches or pixels; error, pixel and invalidation contracts are unchanged.

For nonidentity transforms with at most 1024 active vertices, a separate Display-shared scratch area can compute once, fully validate and then commit. Scratch counts against the VM as `min(vertex_capacity,1024)*16` payload bytes plus userdata overhead; multiple meshes reuse capacity. First use or growth may allocate, and old/new allocations can coexist during growth. Display release or VM teardown releases the shared reference. Above 1024 active vertices, the original two-pass validation/transform path remains; the public 65536-vertex limit is unchanged. Scratch borrows neither source vertices, committed positions nor complete span candidates. After any potentially reentrant allocation, mesh and Display state are reread. No allocation or callback occurs between complete validation and publication. Failure does not undo valid user-finalizer changes or overwrite them with stale outer state.

Private native computation modules create/update the same userdata through the production public header `h2_lua_display.h`, then pass it to `display.draw_mesh`. See the Doxygen-generated [Lua Display API Reference](/references/lua) from that header for complete C API arguments, errors and ownership contracts. Native indices start at 0, unlike Lua tables. Native updates allocate nothing and do not grow the Lua stack; callers reserve two free stack slots. Creation handles OOM through protected Lua calls and restores the stack on failure. These APIs do not open Display, draw or expose internal storage addresses. Modules must not acquire job/framebuffer access or include private runtime headers. Applications calculate policies such as fish-body deformation, scene projection, color separation and mesh selection first.
