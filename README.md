# GizMoth

A desktop app for GizOS devices: pair a device over Bluetooth, adjust it, and build Lua apps with an embedded coding agent, then push them to the device.

Built with Tauri 2, React and TypeScript. The coding agent is [pi-agent-core](https://www.npmjs.com/package/@mariozechner/pi-agent-core) running inside the app and talking to whichever model provider you configure.

## Features

- **Pairing**: GizOS BLE Binding v1 over native Bluetooth, or a device credential link. The compact nearby-first dialog starts scanning only on request, keeps scan/stop inline, and marks the selected row while connecting. A secondary disclosure reveals a masked credential-link field; cancellation and unmount ignore late UI results. BLE and backend behavior are unchanged. Device API keys use private files in the app data directory; Device information supports reveal, replacement, and explicit migration of an old OS-store key.
- **Device management**: a bounded control-center overview with compact square volume, display and light controls. Selecting a square expands a dark adjustment panel with a luminous screen, a rounded hemisphere lamp with fine triangular facets and a base at the bottom, or an upward sound cone; drag vertically or use the keyboard to adjust. Click outside or press Escape to dismiss; dragging from the control into the backdrop never dismisses it. An identity card pairs the device's 3D model tile, dimmed while offline, with its name, model and connection, and a strip of battery, Wi-Fi, cellular, Bluetooth and microphone readings; offline devices show when they were last online and which readings appear once they reconnect. Device information expands the address, firmware version and device key below the strip. Confirmed device removal remains a red action at the top right. Installed Lua applications appear as independent iPhone-style home-screen icons. Clicking one opens a compact identity header, separate device and simulator sections with destination-local availability and feedback, and a confirmed-delete footer. Source/profile controls appear when matching local source is available for sending a snapshot to an independent simulator. If there is no simulator, the dialog offers inline creation by name and model, even without local source; creation saves an independent profile and selects it without leaving the dialog. A device application without a matching local project cannot be simulated because the device API does not expose its source. Search, supplied metadata in tooltips, project installation, and per-app Open-request feedback remain available. Success copy confirms a request or demo simulation, not verified runtime execution. Library glyphs are local fallback artwork because the device API does not expose app icons.
- **Projects**: local Lua projects (`app.json`, `<app_id>.lua`, assets under `<app_id>/`) with an editor, autosave and package checks against the firmware's rules. Discovery uses compact single-line rows inside one white card with separators, no table header, and a 1040px maximum content width.
- **Coding agent**: the agent lists, reads, writes and edits project files, runs the package check, and can push to the selected device, asking first unless the project's permission says otherwise. Each project has one conversation, saved locally after every finished message. It runs in a background session: leaving the project page detaches the view while the assistant keeps working, quitting mid-run keeps the prompt and completed steps, and the unsent draft (text and images) is kept per project. Deleting a project disposes its session. Installing an app update is refused while any project's assistant is still running, and every session saves first. The 清空对话 broom at the start of the chat toolbar empties it after confirmation. Messages show their time and actions on hover (the latest reply keeps them visible): copy a prompt or a whole reply turn, rewind from a prompt (after an inline confirmation under the message it removes that prompt and everything after it and puts its text and images back in the input; files already changed are not reverted), and regenerate the latest reply. A project brief (项目说明) is kept: the assistant updates it with its `update_project_brief` tool (up to 2000 characters) after meaningful changes, it is appended to the system prompt as quoted data, and you can edit it in the project information panel. The conversation and input share a centered reading column. A compact single-line input grows for longer prompts. Attach up to four PNG, JPEG, GIF or WebP images with the paperclip, by pasting or by dropping them on the input; large images are scaled to 1568px and re-encoded as JPEG, and a message can be images alone. Attaching is disabled, with an explanation, when the selected model does not accept images. Sent messages show their images, and saved history drops the oldest image data once it would exceed 7 MiB. Below the input, right-aligned, sit only things you can change: one model trigger showing the model name and thinking level, plus a context-usage ring once the provider reports usage. The ring opens a 上下文窗口 popover with used / total, a bar, and the input, cache and output tokens of the latest reply. From 75% it turns amber and offers 清空对话…; from 90% it turns red. The trigger opens a searchable flat model list (name · provider, context window, thinking support) and a 思考程度 row whose submenu sets the thinking level, all keyboard-accessible. Thinking choices follow SDK model capabilities, persist per project and reach the actual request. Consecutive tool calls collapse into one summary line that shows progress and failures and expands to the individual calls. The send icon turns into a spinner while the assistant works; press Esc to stop (there is no Stop button). Completion, errors and stopping settle the UI; completed reasoning folds away and old unresolved tool calls do not keep spinning. Composition keystrokes do not select, navigate, dismiss or clear the picker; synthetic browser events were verified, while OS IME behavior remains untested. Project file tools are bound to the selected project ID and Rust directory capabilities, rejecting traversal and symlink escapes; writes use exclusive temporary files and atomic replacement. There is no shell. Assistant permissions are set per project in 项目信息 › 助手权限 and stored in `agent-permissions.json`; the system prompt states the current settings.
  - **Files outside the project** (不可访问 / 只读, the default / 读写) means the user's home folder, reached through `list_home`, `read_home` and `write_home`. Access is enforced natively with cap-std: every path component is opened without following symlinks from a pinned home directory. Credential locations (`~/.ssh`, `.gnupg`, `.aws`, `.azure`, `.kube`, `.docker`, `.netrc`, `.password-store`, `.config/gh`, `.config/gcloud`, `Library/Keychains`, `Library/Cookies`) and GizMoth's own app data are always refused, and writes to hidden top-level entries and `~/Library` are refused even with 读写. Reads and atomic writes are limited to 1 MiB, listings to 500 entries.
  - **Push to device** (每次询问, the default / 直接运行 / 禁止) is applied by the `push_to_device` tool.
  - **Web access** (允许, the default / 禁止) gates `fetch_url` and `web_search`. `fetch_url` uses the native `web_fetch` command: http/https only, no credentials in the URL, public addresses only (loopback, private, link-local, CGNAT/Tailscale and ULA ranges are refused, and the DNS answer is pinned), redirects reported rather than followed, a 20 s timeout and a 2 MiB cap; HTML is converted to text. `web_search` uses Brave Search or Tavily, configured in Settings › 联网搜索; its key is kept in the OS credential store under the service `com.gizclaw.gizmoth.search`, and `search.json` holds only the choice of provider. Files and web pages are treated as untrusted data.
- **Development workspace**: the primary sidebar's Projects sub-list contains Lua applications, Giz firmware, and native firmware. Selecting a category filters project discovery; selecting Projects shows all projects. An open project starts in AI chat with code hidden. Show code reveals chat on the left and the editor on the right in wide windows; narrow windows switch to the editor with a return-to-chat action. Both panes stay mounted to preserve edits and conversation state. A single Run action opens a target chooser for hardware devices or independent simulators, then runs on the chosen target. The chat pane has its own compact header, with clear conversation, project information, Run, a `{}` code toggle and the project menu grouped at its upper right. Project information opens a column with the project brief, type, app ID, files, package check, run target and the assistant's per-project permissions; it sits beside the panes when there is room and otherwise floats over the right edge. In wide windows a draggable, keyboard-accessible divider sets the chat width, which is remembered. The panel shows no version; `app.json` and the package manifest still carry a SemVer version (0.1.0 for new projects) because the firmware package format includes it. These controls align with the neighboring file-tab strip and do not live in the application titlebar. Checks, export and project deletion live in that menu. The code pane has closable file tabs, content search, manual formatting and an optional right-hand directory tree with filtering and expandable folders. File actions remain local to that pane. Clickable file-path breadcrumbs list each segment's siblings under its parent in an expandable HTML tree popup; selecting a file uses the existing save-before-switch flow. Arrow keys, Home/End, typeahead, Enter/Space and Escape provide keyboard navigation and focus restoration. The chooser stays within the project, while rename remains in the file-actions menu. The path bar also offers automatic language detection from the extension or a per-file override for Lua, JSON, JavaScript, TypeScript, HTML, CSS, Markdown, YAML or plain text. Selection changes syntax highlighting and formatting without renaming the file; overrides last only within the open workspace. Use the Format icon or Shift+Alt+F to format and save the active source file. Formatting uses two-space indentation and a 100-column target; plain text cannot be formatted. Syntax errors leave the source unchanged and display an error. The existing 500 ms autosave saves edits without formatting. The workspace has no bottom status bar or idle saved label. Saving, busy operations, results and errors appear in the shared titlebar with truncating text and a spinner, check or warning glyph; non-error results clear after six seconds and errors remain until replaced. There is no persistent target dropdown, separate simulator launcher or code/pi-agent mode selector.
- **Simulators**: the primary sidebar's Simulators page creates, edits, opens and deletes named independent simulators. Its single-card list matches Projects with 48px single-line rows for name, model, firmware choice and actions. Each profile opens a resizable Tauri window with a merged macOS overlay titlebar; browser previews use a popup. The device stage fills the window between a compact model/view toolbar and a single hardware-button row. Firmware settings and keyboard help open on demand and dismiss with outside click or Escape; the status strip keeps runtime support visible. Reopening the same profile focuses its existing window, and closing it leaves the editor running. The simulator manages its model, firmware, power and view without a project association. Workspace and device-app actions can send a temporary application install/run request to a selected profile, using unsaved editor content when available and saved source otherwise. Select an SDK-supported H106 model and compatible provider firmware, then explicitly install that selection and start it in a capable native simulator WebView or isolated browser. Left/Right/OK/Back/Power preserve device-button semantics with scoped keyboard input and pointer holds; the framebuffer and installed-app execution requests use that runtime. The provider currently offers trial firmware; raw device ROM/bin images are not Web runtime firmware.
- **Appearance and language**: Settings offers System / Light / Dark themes and System / 简体中文 / English languages. Both default to System and persist across restarts. The app interface, documentation reader and native tray share the language preference; explicit choices override the system, while System uses Chinese for Chinese locales and English otherwise. The editor, menus, dialogs and simulator chrome use the same theme palette. Open windows update without clearing edits or drafts. Native preferences live in `desktop.json`; browser demos use localStorage. `src/theme.ts`, `src/language.ts`, `src/appearance.ts`, `src/i18n.ts`, `src/locales/` and `src/theme.css` own the shared frontend contract.
- **Desktop shell**: titlebar identity and version, collapsible navigation, device connection, project search, and explicit Lua/Giz/native-firmware project categories. Launching another instance shows, unminimizes and focuses the existing main window. Lua applications use GizOS Lua Runtime and can run in compatible browser, phone, and MCU environments. Lua creation is implemented; the firmware categories are marked as not yet connected.
- **Menu bar / system tray**: a compact native menu shows the application version and paired-device count, with a submenu of saved simulators by name and model. Selecting a simulator opens or focuses its independent window, including while the main window is hidden. Device and simulator changes refresh the menu; device management, simulator management, Settings and Quit are available without expanding a wide panel.
- **In-app updates**: a titlebar prompt appears only when a newer signed release is available. The far-right Update badge starts download, byte-based progress, signature verification, project preparation, installation and restart with one click. Unknown download sizes show downloaded bytes rather than an invented percentage. Failed downloads or installs can be retried. Installation saves the open editor first and is blocked while project operations or the coding agent are active.
- **Providers**: magpie (local gateway), Anthropic, OpenAI, Google Gemini, OpenRouter, DeepSeek, or any OpenAI- or Anthropic-compatible endpoint. Model lists can be read from the provider's API or entered by hand.
- **Push**: package (format-1 manifest, SHA-256, deterministic USTAR + zlib) and install directly to the device, then start it. Packages can also be exported as `.lua-app.tar.zlib`.

## Install

Download the latest installer from [Releases](https://github.com/GizClaw/gizmoth/releases): the `.dmg` for macOS (Apple silicon or Intel) or the `.exe` for Windows.

## Development

Use Node.js 22.13 or newer, Rust 1.90 or newer, and the Tauri platform prerequisites. Install JavaScript dependencies with `npm ci`, then run `npm run app` for the desktop application.

`npm run dev` starts the Vite UI on port 1420. Add `?demo=1` for development-only in-memory devices and projects, or `?demo=1&view=device` to open the demo device's detail page directly. Even model-only previews need Web Crypto (`crypto.subtle.digest`) to verify downloaded assets. Use HTTPS for remote access or a loopback browser preview on the host Mac; plain HTTP on a LAN or Tailscale IP can display the UI but cannot load verified models. The development server also supplies COOP/COEP headers for `models-player` trial firmware, which needs a secure, cross-origin-isolated browser context with SharedArrayBuffer. These headers do not make a remote HTTP address secure.

Run `npm run build`, `npm test`, and `cargo check --manifest-path src-tauri/Cargo.toml --locked` to validate changes.

## Native integration tests

Run the isolated Tauri suite with:

```bash
npm run test:tauri
```

It builds a debug-only `native-e2e` app with its own identifier, temporary application data and incognito webview, then drives the real native UI and IPC using an embedded WebDriver. A deterministic loopback model server supplies responses; tests do not use real providers, credentials, devices or user projects. The driver cannot be compiled into release builds. macOS and Windows have a dedicated CI matrix; local execution has been verified on macOS.

The fifteen native scenarios cover persisted appearance/language preferences and documentation synchronization, in addition to completed thinking/replies and subsequent sends, failures, stopping with Esc including a completely silent SSE connection, reasoning request parameters and persistence, historical orphan tools, current-project filesystem boundaries, runs that continue and save in the background after leaving a project, the project brief surviving a cleared conversation, home-folder access following the project setting without reaching credentials, regenerating or rewinding from a prompt, HTML dropdown keyboard/focus behavior inside and outside modal dialogs, and workspace breadcrumb navigation with save-before-switch and titlebar feedback. The workspace case in `test/integration/workspace-navigation.test.mjs`, imported by `test/integration/agent.test.mjs`, exercises explicit focus when macOS clicks do not focus buttons, root and nested siblings, folder arrows, Escape focus restoration, saved edits before switching and absent idle feedback, without sending a model request. This describes scenario coverage, not a passing result for the current refinements. The harness gives the app a fake home through `GIZMOTH_E2E_HOME`, which the app accepts only when that folder contains the harness marker file. Failure diagnostics and screenshots are written to `src-tauri/target/native-e2e-results/`. Reuse the already built test binary with:

```bash
npm run test:tauri:run
```

The HTTP plugin is pinned through a small local 2.8.3 patch so cancellation interrupts a native body read even if the server sends no further chunks. Upstream provenance, scope and removal criteria are documented in `src-tauri/vendor/tauri-plugin-http/PATCHES.md`.

## Releases and updates

CI validates the frontend and Rust checks on macOS and Windows, and builds macOS ARM/Intel and Windows NSIS installers with locked Cargo dependencies. Ordinary CI deliberately disables signed updater artifacts because pull requests do not receive release secrets.

For a release, the stable `vX.Y.Z` tag must exist and match `package.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`. The Release workflow also supports manual dispatch with that explicit tag. Configure repository secrets `TAURI_SIGNING_PRIVATE_KEY` and, for an encrypted key, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the private key must match the public key pinned in `tauri.conf.json`. Never generate a replacement key for each release or commit private signing material.

Release jobs build signed updater archives/installers for all three targets. A single final job checks the artifact set, verifies each signature against the application's public key using Minisign, and uploads `latest.json` last to a draft GitHub release. Publishing that draft remains a separate action. Existing releases or moved tags are refused rather than mixing artifacts from different runs. Apple Developer ID/notarization and Windows Authenticode certificates remain independent optional signing inputs listed in the workflow.

Installed apps check `https://github.com/GizClaw/gizmoth/releases/latest/download/latest.json`. No prompt appears before a newer published release exists. Checks run at startup, every hour, and when the network comes back online. One explicit Update click downloads and verifies the release, saves the open project, then installs and restarts; on Windows the installer exits/restarts the app, and on macOS GizMoth relaunches after installation. The first updater-enabled build must be installed normally before future in-app updates can work.

For UI-only validation, `?demo=1&update=available` shows a simulated update, `update=error` demonstrates download failure/retry, and `update=unknown` demonstrates a missing download size. These development-only fixtures never install or restart the computer's app.

| Editor | Tabbed code pane, project file breadcrumbs/tree, language detection/selection, text-only formatting | `src/pages/CodeWorkspace.tsx`, `src/pages/CodeWorkspace.css`, `src/pages/FileBreadcrumbs.tsx`, `src/pages/FileBreadcrumbs.css`, `src/Editor.tsx`, `src/project-files.ts`, `src/editor-language.ts`, `src/editor-format.ts`, `src/editor-lua-browser.ts`, `src-tauri/src/formatter.rs` |
| Device icons | Model-specific SDK glyphs, theme-aware masks and unknown-device fallback | `src/pages/DeviceIcon.tsx`, `src/pages/Devices.tsx`, `@gizclaw/models-player/icons` |
| Simulators | Named independent simulators, profile windows, temporary application snapshots | `src/pages/SimulatorManager.tsx`, `src/simulator-profiles.ts`, `src/simulator-window.ts`, `src-tauri/src/simulator.rs`, `src-tauri/src/simulator_runtime.rs`, `src/preview-project.ts` |

Packaged simulators load bundled entry/assets inside a Tauri WebView from an ephemeral `127.0.0.1` port; they do not launch an external browser. `simulator_runtime.rs` checks the Host header and supplies COOP/COEP plus a simulator-specific CSP admitting the reviewed Blob iframe, workers and WASM, with connections to `static-volc.gizclaw.com`, `ap.dev.gizclaw.com` and `ap.gizclaw.com`. The main application CSP remains unchanged. Custom permissions in `src-tauri/permissions/application.json` and the simulator capability expose only simulator preferences and temporary-package commands alongside scoped core/asset access; main device, provider and project-file commands are inaccessible to simulator windows.

Native source requests use targeted, token-checked Tauri events across the separate origins. Browser fallback retains same-origin, source-checked `postMessage`. Native temporary Lua packages are built client-side and delivered by the runtime from memory: at most 512 KiB each, 32 live packages, a ten-minute TTL, and deletion restricted to the owning window. They are not persisted in simulator profiles.

Lua formatting uses StyLua 2.6 with Lua 5.4 syntax and output AST verification: native builds call Rust through the main-window `format_lua_code` command on a blocking worker; browser demos use the same formatter version through WASM. Other supported source languages use Prettier standalone with bundled plugins. Formatting accepts at most 2 MiB of UTF-8 source and does not execute source or project-owned plugins. Native Lua formatting does not require broadening the main application CSP for WASM.

The single-instance plugin is registered first in `src-tauri/src/lib.rs`; its activation callback restores the main window through `desktop_state::show`.

Only the OpenAI, Anthropic and Google provider APIs of pi-ai are bundled; other SDKs are stubbed out in `vite.config.ts`.

## Local data

- Device API keys: app data `private/<device-id>` files, with Unix permissions `0700` on the private directory and `0600` on newly written key files. `devices.json` holds metadata only. Normal connection reads, reveal, save and removal never access Keychain or another OS credential store. Only explicit migration reads an old OS-store key and attempts to remove that copy after saving locally; manual re-entry is also supported.
- Provider API keys and the web search key still use macOS Keychain, Windows Credential Manager or Linux Secret Service.
- Device metadata, provider configuration (without keys), projects and per-project agent conversations: the Tauri app data directory (`projects/<id>/`, `chats/<id>.json` as `{ format: 2, brief, messages }`, with legacy bare message arrays still loading, `devices.json`, `providers.json`, `agent-permissions.json`, `search.json`).
- Simulator profiles: native `simulators.json` stores each profile's ID, name, `model`, `firmwareId` and `view`; browser previews use localStorage. Profiles contain preferences only: no project association, source, installed firmware or running runtime state. Legacy project links are ignored on read and dropped on the next save.

Provider requests may go to any HTTPS URL, or HTTP on `localhost`/`127.0.0.1`. Device requests are HTTPS only, with redirects disabled so credentials are not forwarded. Mutating device requests are never retried automatically; after a timeout, refresh before trying again.

## Bundled GizOS documentation and MCP

The sidebar's **文档** page is a bilingual documentation center for the whole GizOS platform. Its grid fills the main workspace, with 224px topic navigation and the reader scrollbar at the far right; only the centered reading column is capped at 72ch. Its nine areas cover getting started, Lua apps, native applications, Runtime/PAL, libraries/protocols, boards/platforms, build/toolchains, firmware/installation and testing. Lua App development is one area, leaving room for future development workflows. The committed Markdown in [`docs/gizos/`](docs/gizos/README.md) provides 20 complete Chinese/English guides and two application examples. The reader and MCP publish curated development content only: no raw headers, source mirrors or archive collections. The reader follows the App language selected in Settings: System, 简体中文 or English. In System mode, Chinese locales use Chinese and other locales use English. Guide content and navigation update together, with no separate documentation language picker. Source citations remain document-footer links. Search, code/Markdown copying, tables, links and keyboard-scrolling code work offline without a model provider. Builds preserve the Markdown in browser assets and `$RESOURCE/gizos-docs/`; on macOS this is `GizMoth.app/Contents/Resources/gizos-docs/`.

Every project automatically connects to the bundled `gizos-docs` MCP before its first model request. It exposes `gizos_docs_search` and `gizos_docs_read`, plus paginated MCP resources, using the official MCP SDK's in-memory transport. Tools accept a `language` (`zh-CN` or `en`) and search can filter by development `section`; legacy `gizos://lua/...` resource URIs remain readable. There is no extra TCP port, daemon, Node installation or user configuration required inside GizMoth. The docs are read-only and independent of web/home-folder permissions. The system prompt instructs the agent to consult the built-in docs instead of asking the user to supply known GizOS interfaces.

The human reader and MCP use the same Markdown bytes. Runtime sources are pinned to GizOS `75deb77229d3fb07dd10d39683c69009b1eb45e9`; the official prose is separately pinned to `81e8cbfc64760b5bcc89e8be771393662e876ea5`, before it was removed from the upstream guides. The updater verifies that `libs/lua` is unchanged between those revisions. Source paths, line origins, revisions, content hashes and upstream licenses are retained. Firmware still needs the documented capabilities and launcher-provided button IDs; docs and package validation do not establish successful execution on a particular device.

Normal builds need only the committed Markdown, not a GizOS checkout or network. Refresh generated assets after editing documentation with:

```bash
npm run docs:gizos:bundle
```

Maintainers can update the pinned references in `src/gizos-docs/sources.json` and import them from a local GizOS checkout:

```bash
npm run docs:gizos:update -- /path/to/GizClaw/gizos
```

Add future areas through `src/gizos-docs/sections.json` and paired guide entries in `docs/gizos/localized-guides.json`; the reader and MCP discover the same metadata. Recheck translations when their sources change.

Other MCP clients can use the same server over stdio from this checkout. Configure their command as `node`, with the following script and flag as its arguments (use an absolute script path in client settings):

```bash
node --experimental-strip-types scripts/gizos-docs-mcp.mjs
```

The native integration suite scripts a model through docs search/read, Lua file writing and package validation with internet/home access disabled; the documentation server, agent, WebView and project IPC are real. This validates integration, not unscripted model behavior or hardware gameplay.

## Limitations

- Direct install is limited to 512 KiB compressed; larger packages need a device-reachable URL, which GizMoth does not host.
- Project payloads are UTF-8 text only; binary assets are not supported yet.
- The agent has bundled GizOS Lua Runtime API docs and examples, but the selected firmware must supply the documented Display, input and Time capabilities. Runtime compatibility and physical-button routing still require target-specific verification.
- Real-device interoperability (BLE binding, install, run, controls) still needs hardware verification on each platform.
- The separate simulator uses provider-admitted Web firmware. Snapshot transport, native and development package delivery, and temporary application install/run requests are implemented. Packaged macOS firmware installation and start have been observed without Vite. The local breathing-light package was accepted for installation, but its run request was rejected by the selected Trial firmware; successful application execution and full gameplay remain unverified. A queued application request waits for compatible firmware to be installed and started. Persisted profiles do not restore an installed or running runtime.
- Web firmware requires Web Crypto, `crossOriginIsolated` and SharedArrayBuffer. Execution is gated by these actual capabilities, including in native windows; missing capabilities still produce explicit errors. Packaged macOS firmware start does not establish full gameplay or compatibility on Windows or Intel Macs, which remain untested.
- Giz firmware, native firmware (the internal `rom` project kind), h2loader serial scanning, and firmware/loader installation are recorded product requirements; their build and flashing pipelines are not implemented yet.
