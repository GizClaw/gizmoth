# Product

## Platform

web

## Users

GizMoth primarily serves makers and hobbyists working with GizClaw devices and GizOS. They are willing to understand their hardware and work with code, and want to turn ideas into working device behavior through Lua applications or direct firmware development.

## Product Purpose

Help a maker turn an idea into a working feature on a real device. GizMoth brings device management, firmware and loader installation, Lua application development, and direct firmware development into one desktop product.

The product has four confirmed areas:

1. **Device management:** list and control GizClaw devices.
2. **Serial installation:** scan for h2loader serial ports and install firmware or a loader, following the role of GizOS's gizloader.
3. **Lua application development:** build Lua applications for GizOS Lua Runtime with an integrated pi-agent. These applications can run across environments including browsers, phones, and MCUs; each environment needs a compatible runtime.
4. **Firmware development:** develop firmware directly, with **Giz firmware** projects distinguished from **native firmware** projects built and flashed directly using toolchains such as ESP-IDF.

Projects therefore have three intended kinds: Lua applications, Giz firmware, and native firmware. Games should be playable on a computer through `models-player`, in a standalone simulator window that can be opened and closed independently of the development workspace. The preview flow is **choose a supported model → choose firmware compatible with that model → install the selected firmware → start it**. Do not silently replace the user's firmware choice with a default. Preview input must preserve the device's button semantics, including `left`, `right`, `ok`, and `back`; keyboard conveniences must not silently change device behavior.

Success means the intended behavior works on the device. Generated code, a package check, or a successful build alone is not that outcome. These areas define the intended scope; their implementation status is recorded below.

## Positioning

GizMoth is a desktop workspace for managing GizClaw devices and creating their behavior at two levels: applications on the Lua runtime and firmware itself. Serial installation connects firmware or loader artifacts to physical hardware; device management covers the device list and controls.

The Lua workflow uses an integrated pi-agent alongside inspectable, editable project files. Firmware development is a distinct product capability; its toolchain and agent integration have not yet been specified.

## Operating Context

- The product ships as a Tauri desktop application for macOS and Windows. Its interface uses React and web technologies inside a WebView; the platform classification above describes that interface, not a browser-hosted service.
- Existing device management pairs devices through native Bluetooth or a device credential link, then uses the paired device's HTTP API for supported operations.
- The required serial workflow must discover h2loader serial ports and support installing firmware or a loader, with GizOS's gizloader as the functional reference. This workflow is not implemented yet.
- Users configure a model provider and available models for the Lua coding assistant. Assistant requests depend on that provider's connectivity and configuration.
- Projects, conversations, device metadata, provider settings and simulator profiles are stored locally. Device API keys use app data `private/<device-id>` files (`0700` directory and `0600` written files on Unix); `devices.json` contains no secrets. Normal device-key operations do not access the OS credential store. Users may explicitly migrate an old key or enter it again; provider API keys still use the OS credential store. Local storage does not imply that model inference runs locally.
- The Lua loop starts with pi-agent conversation and optionally revealed code, package checks, and a unified Run target chooser for hardware devices or independent simulators. Device management is also a product area in its own right.
- The current interface is primarily Simplified Chinese, with technical identifiers and terms such as Lua, Provider, and API key retained where used in the product.

### Required capabilities not yet implemented

- Discover h2loader devices through serial-port scanning.
- Install firmware or a loader through the serial workflow, with behavior informed by GizOS's gizloader.
- Create direct Giz firmware and native firmware workflows alongside Lua application development, including the appropriate build and installation paths.

These are confirmed product requirements, not claims about the current application.

### Current limits

- Existing device support follows the GizOS binding, Lua package, and device API contracts referenced in `docs/maintenance.md`. Serial and firmware workflows must be grounded in their actual protocols and toolchains when implemented.
- Direct Lua package installation is limited to 512 KiB compressed. Larger Lua packages require a device-reachable URL; GizMoth does not host those packages. This limit is not a specification for firmware or loader images.
- Lua project payloads currently support UTF-8 text, not binary assets. Firmware and loader artifact handling must be specified separately.
- Bundled documentation is pinned to a verified GizOS source revision. Device/firmware capabilities and launcher-provided component IDs can differ; access to API docs and passing package checks do not establish successful gameplay or arbitrary hardware behavior.
- Controls depend on capabilities declared by the device. Unsupported controls must not be presented as working capabilities.
- Existing device-changing HTTP requests are not automatically retried after timeouts; users need to refresh the state before retrying.
- Real-device interoperability for pairing, Lua installation, execution, and controls still requires verification on each platform. A browser demo or package check is not evidence of that verification.
- Trial Web firmware execution requires Web Crypto, `crossOriginIsolated` and SharedArrayBuffer; actual capabilities determine availability in both native and browser environments. Missing capabilities retain explicit errors. Windows and Intel Mac simulator execution remain untested. The verified Lua framebuffer probe does not establish gameplay compatibility for every app. Trial firmware can temporarily detach local control while network tasks stop or rebuild and while a Lua app owns device resources. Use the device's Back long-press to exit an app before sending another project; short-press Power if its backlight has gone to sleep.
- The preview can switch between the model and its public framebuffer without creating a second runtime. Starting the runtime and powering the simulated device are separate actions; hardware long-press behavior is preserved.

### Open product decisions

- native firmware uses direct build/flash toolchains such as ESP-IDF. Exact templates, Giz firmware build tooling, local build environments, and firmware-specific agent or debugging support remain to be specified.
- Exact h2loader detection and installation behavior must be established from the GizOS gizloader implementation and relevant protocol documentation. Supported boards, firmware and loader artifact sources, and recovery behavior remain to be defined.
- The first complete maker scenario to validate on real hardware, including the required device API guidance, is not yet specified.
- Settings supports System, Simplified Chinese and English App languages, plus System, Light and Dark themes. Defaults follow the system; explicit choices persist and synchronize across windows. Documentation follows the App language. Language/theme changes preserve open projects, unsaved edits, chat drafts and active simulator state.

## Brand Commitments

- Use the actual existing website fonts, locally served unchanged: Montserrat for HTML headings and brand, Monda for ordinary UI, and Lato for assigned metadata, settings group headings and About notes. Keep the Chinese fallbacks and existing code/monospace faces. The user explicitly requires no bold: all explicit UI weights, including heading/strong/table-heading defaults and selected states, are 400, with font synthesis disabled. Bundled WOFF2 files and SIL Open Font License 1.1 texts live in `public/fonts/`.

- Use **Phosphor** (`@phosphor-icons/react`) for regular interface icons throughout the application. Preserve the GizMoth mark and authored hardware-effect geometry as product-specific artwork.
- The application name is **GizMoth**. Preserve the names GizClaw, GizOS, gizloader, h2loader, Lua, and pi-agent when referring to their respective devices, platform, tools, runtime, and assistant.
- Existing identity assets are in `branding/`, including `glyph.svg`, `icon-mono.svg`, and `preview-mono-512.png`; packaged desktop icons are in `src-tauri/icons/`.
- The user supplied magpie's desktop UI as a structural reference: place the app icon, relevant information, and update access in the titlebar; organize primary work around connected devices and projects. Prefer magpie's compact information density and grouped lists over spacious rows and repeated large page headings. Preserve this reference without assuming it defines a new product logo or a mandatory color theme.

## Product Principles

1. Optimize for completing the maker's loop from an idea to observable behavior on a device.
2. Keep Lua application development and firmware development distinct, including their projects, artifacts, validation, and installation paths.
3. Make assistant-created work inspectable and editable so makers can understand and refine what they build.
4. Keep the target device, requested action, and resulting state clear, including approval for assistant-initiated deployment.
5. Respect actual device capabilities, connection state, and workflow-specific limits; distinguish confirmed requirements, implemented behavior, and hardware-verified outcomes.
